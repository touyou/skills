# parallel-review-harness

レビュー対象 (PR 差分・ディレクトリ・設計文書など) を N 個の独立した観点に分解し、観点ごとに独立したレビューアを走らせて、発見をクロス突合するハーネス。特定のレビュードメイン (セキュリティ等) に依存せず、「複数の独立した視点でレビューし、発見の確度を相互検証したい」場面全般に使う。

特定のエージェント製品にも依存しない。実行環境の能力を自己診断して、使える最も強いモードに自動フォールバックする。

## 鉄則

- **レビューアを大量起動する前に、観点リストをユーザーに承認させる**。観点の数 = 起動するレビューアの数 = コストなので、勝手に増やさない。
- **各レビューアは互いの結果を見ない** (独立性が突合の価値の源泉)。プロンプトに他観点の発見を混ぜない。
- **突合結果の確度を偽らない**: 片系統でしか出なかった発見を「両系統一致」と同格に報告しない。
- **このスキルは発見と格付けまで**。修正・コメント投稿・approve は行わない (必要なら `pr-review-loop` や `review-followup` に引き継ぐ)。

## Step 1: 実行環境の自己診断

以下を順に確認し、モードを決める:

1. **並列サブエージェント**: このセッションでサブエージェント (Task/Agent ツール等) を並列起動できるか
2. **シェル実行**: シェルコマンドを実行できるか
3. **別ベンダーのエージェント CLI**: `codex` / `gemini` など、自分と異なるベンダーのエージェント CLI がインストール・認証済みか

```bash
command -v codex >/dev/null && codex --version    # 例: Codex CLI
command -v gemini >/dev/null && gemini --version  # 例: Gemini CLI
```

| モード | 条件 | 構成 |
|---|---|---|
| **A: 二系統クロス** | 並列実行手段が 2 系統ある | 系統 1 = サブエージェント N 並列、系統 2 = 別ベンダー CLI を N 並列 (同じ観点セットを両系統に与える) |
| **B: 単系統並列** | 1 系統だけ | サブエージェント並列 or CLI fan-out のどちらかで N 並列 |
| **C: 逐次マルチパス** | シェルもサブエージェントも無い | 観点ごとに独立したレビューパスを 1 つずつ順に実施 (前のパスの発見を次のパスのプロンプトに持ち込まない) |

選ばれたモードと理由を最初に 1 行で報告する (例: 「Codex CLI が見つかったのでモード A で実行します」)。

## Step 2: 観点の設計と承認

レビュー対象に合わせて観点を提案する。ドメイン別の観点セット例:

| ドメイン | 観点例 |
|---|---|
| コードレビュー | 正しさ / エラーハンドリング / テスト妥当性 / 型設計 / 可読性 |
| セキュリティ | 入力検証 / 認証認可 / シークレット露出 / 依存脆弱性 |
| アクセシビリティ | 視覚 (コントラスト・Dynamic Type) / 操作 (タップターゲット・キーボード) / 支援技術 (VoiceOver ラベル) |
| 設計文書 | 整合性 / 抜け漏れ / 実現可能性 / 運用負荷 |

提案フォーマット (**ユーザー承認を得てから起動する**):

```markdown
対象: PR #123 (差分 12 ファイル)
モード: A (二系統クロス: サブエージェント + Codex CLI)
観点 (4): ①正しさ ②エラーハンドリング ③テスト妥当性 ④型設計
→ 起動するレビューア: 4 観点 × 2 系統 = 8。進めてよいですか？
```

既存の専門スキル (例: `apple-accessibility` のチェックリスト) がある観点は、そのスキルの基準をレビューアのプロンプトに引き込む。

## Step 3: レビューアの起動

各レビューアに渡すプロンプトの型:

```text
あなたは「<観点>」専任のレビューアです。<対象> を <観点> の視点だけでレビューしてください。
- 他の観点 (例: <他観点の列挙>) には言及しない
- 発見ごとに: 場所 (file:line)、内容、根拠、重大度 (🔴/🟡/🟢) を出す
- 発見が無ければ「無し」と明言する (無理に絞り出さない)
```

- モード A: 同じ観点プロンプトを両系統に与える (系統間で文言を変えない — 差が出たとき原因を観点差ではなく系統差に帰着させるため)
- モード C: 各パスの開始時に前パスの発見を要約に含めない。コンテキストに残ってしまう場合は「前パスの発見は忘れて <観点> のみで見る」と明示する (逐次モードの独立性は近似であることをレポートに明記)

## Step 4: クロス突合と確度格付け

全レビューアの発見を (file, 行範囲, 要旨) で突合する:

| 検出パターン | 確度 | 扱い |
|---|---|---|
| 両系統で一致 (モード A) | **高** | 確度を格上げして最上段に報告 |
| 同一系統内の複数観点で一致 | 中〜高 | 「複数観点が指摘」と明記 |
| 片系統のみ / 単一レビューアのみ | 中 | その旨を明記して報告 (捨てない) |
| 系統間で矛盾 (一方は問題なし、一方は指摘) | 要検証 | 矛盾として明示し、可能なら根拠を読み比べて判定、できなければユーザーへ |

モード B / C では「両系統一致」の行は出ない。レポート冒頭に「単系統のため確度格付けは観点間一致のみ」と断る。

## Step 5: 最終レポート

```markdown
## parallel-review-harness 結果 — <対象>

- モード: A (サブエージェント 4 + Codex CLI 4)
- 観点: 正しさ / エラーハンドリング / テスト妥当性 / 型設計

### 確度: 高 (両系統一致)
- 🔴 `lib/api.dart:42` — エラーを握りつぶしている (両系統・②が指摘)

### 確度: 中 (片系統のみ)
- 🟡 `lib/model.dart:10` — 型の不変条件が弱い (系統1・④のみ)

### 矛盾 (要検証)
- `test/foo_test.dart` — 系統1は「境界値不足」、系統2は「十分」→ 根拠を読み比べた判定: ...

### 観点別サマリ
| 観点 | 系統1 | 系統2 | 一致 |
|---|---|---|---|
| 正しさ | 2件 | 1件 | 1件 |
```

修正まで進めたい場合は `pr-review-loop` (auto-fix) へ、指摘の対応確認は `review-followup` へ引き継ぐ。

## 由来とブラッシュアップ方針

セキュリティレビュー専用スキルの中にあった「実行環境の能力を自己診断して 3 モードにフォールバックする並列レビューharness」を、任意のレビュー観点向けに汎用化したもの。観点セットの実例 (どのドメインでどの分割が効いたか) と、突合の false positive / negative の傾向を集めて、観点テンプレートと格付けルールをブラッシュアップする想定。

## 依存

- (モード A/B) 並列サブエージェント機構、または別ベンダーのエージェント CLI (`codex` 等)
- モード C はどの環境でも動く (フォールバック先)
