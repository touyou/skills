# fresh-session-e2e

配布物 (CLI ツール、npm パッケージ、Agent Skill、テンプレートリポジトリ等) の初回導入 UX を検証するための、ゼロコンテキストセッション起動パターン。スキルやルール文書そのものが対象のときは、同じ起動の仕方で「文書だけを頼りに完遂できるか」を確かめる使い勝手テストも行う（後半の節）。

## 独立した会話と環境を分ける

会話を継承する fork は親の知識が混じり、初見で躓く箇所を素通りしやすい。会話を継承しないサブエージェントでも、共有する作業ディレクトリや設定は初回導入の条件と異なる。このスキルでは空の作業ディレクトリと別プロセスを使って条件を固定する。

別プロセスも HOME・認証・キャッシュ・グローバル設定は継承し得る。「会話なし」と「完全隔離」は同義ではない。再利用した状態を記録し、完全な初回インストールが必要なら対象キャッシュ・設定も隔離する。ユーザーの通常設定を削除して初期化しない。

## 手順

### 1. 検証環境の準備

```bash
WORKDIR=$(mktemp -d /tmp/fresh-e2e-XXXXXX)
cd "$WORKDIR"
```

ルール:

- **`/tmp` 配下の空ディレクトリを使う**。既存プロジェクト内に作ると、そのプロジェクトの CLAUDE.md / AGENTS.md / .claude/ が読み込まれて fresh でなくなる
- グローバル設定 (`~/.claude/CLAUDE.md` 等) の混入が検証の妨げになる場合は、その旨をレポートに明記する (完全隔離が必要ならコンテナ利用を検討)

### 2. 再現プロンプトの固定

検証したいシナリオを**固定の kickoff プロンプト**としてファイルに保存する:

```bash
cat > "$WORKDIR/kickoff-prompt.txt" <<'EOF'
<配布物名> を使って <初見ユーザーがやりそうなタスク> をしてください。
インストールが必要ならドキュメントを探すところから始めてください。
EOF
```

ルール:

- **プロンプトの文言を勝手に変えない**。毎回同じ条件で試すためのもの。改善検証 (before/after) では文言が同一であることが比較の前提
- プロンプトには配布物の内部知識を書かない (README に書いてあること以上をヒントとして与えない)

### 3. 別プロセスでのセッション起動

現在のセッションからは spawn せず、別プロセス / 別ターミナルで起動する:

```bash
# 例: Claude Code をヘッドレスで起動 (現在のセッションとは独立したプロセス)
cd "$WORKDIR" && claude -p "$(cat kickoff-prompt.txt)" > result.log 2>&1

# 例: Codex CLI で同じプロンプトを流す (エージェント間の再現性も見る場合)
cd "$WORKDIR" && codex exec --skip-git-repo-check "$(cat kickoff-prompt.txt)" > result-codex.log 2>&1
```

CLI のローカル `--help` で利用可能なオプションを確認し、モデルと実行時間・費用の上限を設定する。終了コードとログを保存し、認証待ちや同じエラーで無制限に再試行しない。既存アカウントへの投稿・本番操作は検証の許可に含めない。

自動起動が難しい環境では、ユーザーに「別ターミナルで `cd $WORKDIR && claude` を開き、kickoff-prompt.txt の内容を貼り付けてください」と依頼する形でもよい。**現在のセッション内で完結させようとしてサブエージェントに置き換えるのは不可**。

### 4. 配布チャンネルの指定 (npm 系など)

dist-tag のある配布物は、どのチャンネルを検証したか明示する:

```bash
npm install <pkg>@latest   # 安定版の初見体験
npm install <pkg>@next     # リリース前検証
```

Agent Skill なら「marketplace からのインストール」「symlink でのローカル読み込み」のどちらを検証したかを明示する。

### 5. 結果の評価とレポート

セッションログ (`result.log`) を読み、初見ユーザー視点で評価する:

```markdown
## fresh-session-e2e 結果 — <配布物> (<チャンネル>)

- 検証環境: /tmp/fresh-e2e-XXXX、会話継承なし。共有した設定・認証・キャッシュ、CLI版・モデルを記載
- 対象バージョン / commit / チャンネル、終了コード、固定プロンプトとログの保存先
- 結果: ✅ タスク完遂 / ⚠️ 完遂したが迷走あり / ❌ 躓いて未完遂

### 躓きポイント
1. <どの段階で・何に躓いたか。ログの該当行を引用>

### 改善候補
- README の <節> に <情報> が無く、エージェントが推測で進めた → 追記候補
```

改善を入れたら、同じプロンプト・モデル・導入条件で新しい空ディレクトリに再実行し、before/after を比較する。対象版だけを変え、ほかの条件が変わった場合は併記する。成果物とログを保全した後、この実行の一時環境だけを片付ける。

## 使い勝手テスト（スキル・ルール文書が対象のとき）

導入できるかではなく、**文書の記述だけを根拠に作業をやり遂げられるか**を確かめる。書いた本人のセッションが試しても、実装の文脈で穴を素通りするので配管の疎通確認にしかならない。起動は上の手順 1〜3 と同じく空ディレクトリ・別プロセスで行い、次の点を足す。

### いつやるか

変更のたびには回さない。手順の追加・組み替え、新しいコマンドの組み込み、判断基準の変更のように、スキルの使われ方が変わる編集をしたときに提案し、合意を得てから回す。文言の手直しや挙動を変えない整理では提案しない。

### 被験者の条件

- **モデルは 1 段下の tier にする**（Sonnet など）。賢いモデルほど文書の穴を自力で埋めてしまい、検証にならない。文書が下限の tier を定めているならその下限を使う
- **変更後の文書を読ませる**。インストール済みの plugin ではなく、作業ブランチの skill ディレクトリを読み込ませる。読み込ませ方は、空ディレクトリの中に置く・CLI のプラグイン/スキルのディレクトリ指定を使うなど、ユーザーの通常設定を書き換えない方法を選ぶ。同じ名前のインストール済み版が並んで見えないかを確かめ、どちらを読んだかをレポートに書く。同じリポジトリの CLI も一緒に変えたなら、それも作業ブランチの版に揃える
- **監査できる形で起動する**。最終出力だけでなくツール呼び出しを含むログを残し、あとで同じセッションを再開できるようセッションを識別できる情報も控える。CLI のローカル `--help` で、その手段（構造化出力・セッション ID・再開）を確かめる
- **情報源を絞る**。許すのは、タスク文・作業対象の fixture・対象の文書とそこから参照される先・コマンドに内蔵されたヘルプ（`--help` やツールのスキーマ）・実行結果だけ。リポジトリのソース・docs・git 履歴・Web のドキュメント・過去の会話の memory は読まないよう kickoff プロンプトに書く。リポジトリの中で文書が働くかを見る回では、リポジトリ内の参照は許してよい（その回で何を確かめたいかで決める）

### kickoff プロンプトの書き方

- **ゴールだけを書き、確かめたい機能をほのめかさない**。ページの改名でリンク元を直す機能を見たいなら「タイトルを〇〇に変えて」とだけ頼み、「リンクが切れないように」とは書かない
- **分からないことは推測で補わず「分からなかった」と書いて止まるよう指示する**。推測で埋めると文書の穴が隠れる
- 質問が出て止まったら、その質問自体を「文書だけでは決められなかった箇所」として記録する。回答はユーザーに中継してもらい、テスト実施者が自分の知識で答えない。セッションを再開できる CLI ならその同じセッションに回答を渡して続けさせる。新しいセッションに置き換えると、途中で何に迷ったかが消える

### ガイドライン型の文書

判断基準を並べた文書（AGENTS.md など）には完遂の定義がない。その文書が効くはずの作業をタスクとして与え、文書が読まれたか、その記述が判断の根拠として使われたかを見る。

### 終わったあとの聞き取りと監査

1. 同じセッションを再開し、主な判断ごとに「文書のどの記述を根拠にしたか」「推測で補ったところはどこか」を答えさせる。再開できない CLI なら、kickoff プロンプトの最後で、作業後にこの 2 点を書き出すよう頼んでおく
2. ログから実際に読んだファイルと実行したコマンドを拾い、証言と突き合わせる。禁止した情報源を読んでいたら、その回の結果は文書の評価に使わない
3. レポートには、記述を根拠に進めた判断・推測で補った箇所・質問で止まった箇所・読まれなかった記述を分けて書き、推測で補った箇所と質問で止まった箇所を文書の改善候補にする

## 由来とブラッシュアップ方針

CLI 配布物の初見 UX 検証で「サブエージェントは親のコンテキストを引き継いでしまい fresh にならない」という失敗モードに独立に到達した経験を型化したもの。fork / fresh agent の使い分け原則 (会話を継承する fork は実装意図に引きずられる) と同根。検証対象の種類 (npm / Skill / テンプレート) ごとの手順差分が溜まったら分節化する。

使い勝手テストの節は shokai/agent-skills の skill-usability-test（MIT）の考え方を参考にした。参考元の表示として、ここに残す。
