# security-watch-setup

新しく公開された脆弱性・悪性パッケージ・ランタイムのセキュリティリリースを定期的に調べ、
手元の Mac / PC とリポジトリへの影響を判定して、直せるものは直し、残りは本人に知らせる
**ルーチンを設定する**スキル。チェックそのものはルーチンが毎回行う。このスキルの仕事は、
その人の環境（エージェント・OS・シェル・ランタイムの入れ方・リポジトリの置き場所・
権限の範囲）に合ったルーチンを組み立てて、その環境の定期実行の仕組みに登録するところまで。

## なぜ環境ごとに組み立てるのか

同じチェック手順でも、環境が違うと黙って空振りする:

- 定期実行はユーザーの対話シェルと別の PATH で動く。fish では mise の node、bash では
  Homebrew の node、のように**同じコマンドが別の実体を指す**ことがある
- ロックファイルの種類（npm / pip / Gemfile / Podfile / pubspec …）で見るべき勧告が違う。
  使っていないエコシステムの情報源を毎回読むのは無駄で、使っているのに見ないのは漏れになる
- PR を出してよいリポ（自分がメンテナ）と、報告だけにすべきリポ（他チーム・顧客）の線引きは
  人によって違い、ルーチンが勝手に決めてはいけない
- 定期実行の仕組み（Claude Code の定期タスク、Codex、launchd、cron …）で、プロンプトの
  渡し方・権限・通知の届き方が違う

## ワークフロー

### Step 1: 環境を調べる（聞かずに調べる）

```sh
bash <このスキルのディレクトリ>/scripts/detect-env.sh [リポジトリの置き場所 ...]
```

読み取りだけのスクリプト。OS・シェル・使っているエージェントと定期実行の仕組み・
バージョン管理ツール・**シェルごとに選ばれるランタイムの実体**・gh の認証と所属 org・
リポジトリの置き場所・ロックファイルの種類と件数を出す。置き場所を渡さなければ
`~/Developer`・`~/src`・`~/ghq` などの定番を探す。

出力から、次の 3 つを決める（人に聞かない）:

- **使う定期実行の仕組み**: [references/schedulers.md](references/schedulers.md) の選び方に従う。
  detect-env.sh は「インストールされているか」しか分からないので、**今のセッションで使えるツール**
  （定期タスクの作成ツールなど）も合わせて見る
- **毎回見る情報源**: [references/sources.md](references/sources.md) から選ぶ。「使っている」とは、
  手元にランタイムが入っているか、**ロックファイル・Dockerfile の `FROM`・CI の設定に出てくる**こと
  （手元に PHP が無くても composer.lock や `php:` イメージがあれば入れる）。Dockerfile の
  ディストリ（Debian / Ubuntu / Alpine）は `docker_base_images` から決める
- **ルーチン内のシェル**: `shell_activation` で**バージョン管理ツール（mise / nvm / asdf など）を
  有効にしているシェル**を使う。`login_shell` と食い違ったら `shell_activation` を優先する
  （定期実行で同じランタイムが見えるようにするため）。ランタイムの確認は、そのシェルに加えて
  `runtimes_by_shell` で実体が違ったシェルすべてで行うようにルーチンに書く

Windows ネイティブ（PowerShell のみ）では detect-env.sh が動かないので、同じ項目を
PowerShell のコマンドで個別に確かめる。

### Step 2: 人にしか決められないことだけ聞く

確認するのは次の項目だけ。命名・既定のパス・時刻の細部は自分で決めて、決めた内容を
最後にまとめて伝える。

1. **PR を出してよいリポ**: 自分がメンテナのもの（例: 個人の `<user>/*`、自分のチームの
   org のうち特定のリポ）。`gh_login`（個人アカウント。`gh_orgs` には出ない）と `gh_orgs` の
   一覧を見せて選んでもらう。org は丸ごとではなくリポ名のパターンで決めてもらう。名前の似た
   アカウント・org（`<user>` と `<user>-team` など）は別物として扱う。**既定は「どこにも PR を
   出さない（報告だけ）」**。答えがなければこの既定で進める
2. **報告だけにするリポの連絡先**: オーナー向けの連絡文を誰宛てに書くか（任意）
3. **頻度と時刻**: 既定は平日 1 日 2 回（朝と夕方）。PC が起動している時間帯に置く
4. **レポートの保存先と通知**: 既定は `~/Documents/security-watch/`、通知は OS の通知
   （macOS は osascript）。チャットツールへの投稿は、本人が明示したときだけ設定する
5. **ツールの自動更新の範囲**: 既定は「CLI のセキュリティ修正だけ自動で上げる。GUI アプリと
   再起動が要るものは手順を書くだけ」
6. **（PR を出してよいリポがあるときだけ）Dependabot / Renovate の PR をマージしてよいか**:
   既定は「マージしない（TODO に載せるだけ）」。許すなら条件（ロックファイルだけの変更で CI が緑、など）も決めてもらう
7. **（当てはまるときだけ）どの仕組みに登録するか**: デスクトップアプリ（Claude Code を含む Claude アプリ、Codex アプリ）は
   入っているのに、今のセッションに定期タスクを作るツールがない（CLI から呼ばれた）とき。
   「デスクトップアプリで同じ依頼をすれば、アプリの定期タスクとして登録できる（アプリを開いている
   間だけ動く）」「このまま launchd などで登録する（アプリを閉じていても動く）」の 2 択で聞く。
   答えがなければ launchd などで進める

### Step 3: ルーチンのプロンプトを組み立てる

[references/routine-template.md](references/routine-template.md) が正本の雛形。
`{{...}}` を Step 1・2 の結果で埋め、使っていないエコシステムの行を削る。
組み立てたプロンプトは**それ単体で完結させる**（定期実行は毎回まっさらなセッションで
動くので、この会話の内容を前提にしない）。プロンプトの 1 行目には
`（security-watch-setup <このスキルの metadata.version> の雛形から生成）` と書く
（雛形の `<!-- -->` は登録時に消すので、コメントにはしない）（複数の PC で動かしたとき、
どの雛形から作ったものかを比べられるようにする）。

`{{SCRIPTS}}` には、ルーチンが毎回読める**消えない場所**の絶対パスを入れる。このスキルの
ディレクトリが `~/.claude/skills/`・`~/.agents/skills/`・プラグインのキャッシュなど安定した場所に
あればそこの `scripts/` を使う。一時ディレクトリ（`/tmp`、作業用 worktree など）から読んで
いるときや、プラグインの更新で場所が変わりうるときは、Step 4 で `scripts/` を
`~/.local/share/security-watch/scripts/`（Windows は `%LOCALAPPDATA%\security-watch\scripts\`）に
コピーし、そのパスを入れる。

雛形に入っている次の規律は、環境に関係なく必ず残す:

- 毎回、一次情報を実際に開く。前回のレポートに書いたことを「確認済み」とみなさない
- 公開・リリースの操作（パッケージの publish、本番へのデプロイ、OS の更新）はしない
- 名前の付いた脆弱性（「◯◯2Shell」など）は名前でも検索し、CVE と修正版を確かめる
- ランタイム本体の脆弱性は、ロックファイルではなく実行環境の指定
  （Dockerfile の `FROM`、`.node-version` 等、CI の設定）で判定する
- 判定は「影響あり / 条件を満たさず低い / 対象外」の 3 つ。低い・対象外も件数と理由を残す
- PR を作る前に、同じ修正の PR・ブランチ（Dependabot / Renovate / 他メンバー）を探す
- PR はメンテナのリポにだけ出す。自分で作った PR はマージしない。Bot の PR をマージしてよいのは
  ユーザーが決めた範囲だけで、その範囲でもデプロイを起動するリポ・公開 24 時間以内の版はマージしない
- 悪性パッケージは名前の一致だけでなく、既知の痕跡（ファイル・プロセス）も確かめる
- CA の不信任が出たら、OS・JDK・言語ごとの信頼ストアに残っていないか確かめ、ホーム配下のものは指紋で照合して
  自分で外す。管理者権限が要るものは、貼れば動くコマンドを TODO に書く（ベンダーの更新待ちだけで終えない）
- パッケージマネージャの「公開から一定時間は入れない」設定（mise の
  `minimum_release_age` など）は上書きしない。入れられる時刻をレポートに書く
- 修正版がまだ管理ツール（Homebrew / mise など）に来ていないものは、版と CVE を書いて次回に再確認する
- 修正版より古いランタイムが管理ツールに残っていれば、どこからも参照されていないものだけ消す
- 対話入力（パスワード・2FA）が要るコマンドは実行しない。秘密情報はレポートに書かない
- リポのバージョン指定（`.node-version` など）が実際に効いているかを、リポのディレクトリで確かめる。
  バージョン管理ツールがそのファイルを読まない設定になっていて、指定が黙って無視されることがある

### Step 4: 登録して、1 回動かす

必要なら `scripts/` をコピーしてから（Step 3 の `{{SCRIPTS}}`）、
[references/schedulers.md](references/schedulers.md) の手順で登録する。登録したら
**その場で 1 回実行**して、次を確かめる:

- レポートが保存先にできている
- ランタイムのバージョンが、シェルごとに正しく取れている（取れていなければ PATH の問題）
- `repo_scan.py` が全リポを走査できている（`FETCHFAIL` は権限切れ・削除済みのことが多い）
- 通知が届く

1 回目の実行で PR が作られた場合は、そのリンクを本人に伝える。

### Step 5: 本人に伝える

次をまとめて短く伝える:

- 登録した仕組み・頻度・タスク名（と、止め方・変え方）
- Step 2 で既定値のまま進めた項目
- 1 回目の実行で分かった影響あり・要対応のもの
- 制約（例: 「デスクトップアプリが閉じている時間の分は、次に開いたときに実行される」）

## 運用中にルーチンを直したとき

運用しながら PC 上のルーチンの手順に書き足すことはよくある。そのままだと、その PC だけ手順が
進んで、ほかの PC のルーチンや雛形は古いままになる（ある PC では外れた CA が、別の PC では
「更新待ち」のまま残る、など）。ルーチンを直したら:

- 環境に依存しない書き足しは、このスキルの [references/routine-template.md](references/routine-template.md) にも戻す
  （touyou/skills なら PR。ほかの人のスキルなら harness-intake で起票する）
- 雛形を更新したら、ほかの PC のルーチンも作り直す。1 行目の版で、どの PC が古いか分かる

## 付属スクリプト

- `scripts/detect-env.sh`: Step 1 の環境調査。読み取りのみ
- `scripts/repo_scan.py`: ルーチンが毎回使うリポジトリ走査。Python 3 の標準ライブラリだけで動く
  - `repos` / `sync`（fetch と、クリーンなデフォルトブランチだけの ff-only pull。1 リポ 180 秒で打ち切り、既定の並列は 4）
  - `scan`（origin のデフォルトブランチのロックファイルから、指定パッケージの解決済み
    バージョンと悪性パッケージ名を出す。npm / pip / gem / pod / spm / pub / composer / go / cargo / maven。maven は直接書かれた依存だけ）
  - `runtimes`（Dockerfile の `FROM`、ランタイム指定ファイル、CI の node-version 等、
    package.json の engines、GitHub Actions の `uses:`）
  - 脆弱な範囲に入るかの判定はしない。勧告の affected range と照らし合わせるのはルーチン側

ルーチンからスクリプトを呼ぶときは、このスキルをインストールした場所の絶対パスで書く。
スキルを置いていない環境（クラウドで動くルーチン等）では、同じ処理をルーチンの中で
git コマンドで行うように雛形を調整する。

## やらないこと

- 他人のリポへの PR・push・マージ。チャットツールへの自動投稿（本人が明示した場合を除く）
- GUI アプリの強制終了を伴う更新、OS の更新の自動実行
- 認証情報の取得や保存。gh が未認証なら、`gh auth login` を本人に実行してもらう
