# 音を鳴らす・録るアプリ

音を扱うアプリで、最初に決めておかないと後で直す場所が散らばるもの。チェケラ（touyou/CheckItOut、
サウンドボード）と月屏風（touyou/Tsukibyobu、手続き合成の BGM）で実際に踏んだことを置く（2026-07〜11、iOS 26〜27.2）。`AVAudioSession` や
`AVAudioEngine` の API そのものは Apple のドキュメントが正本。

## セッションのカテゴリを場面ごとに決める

カテゴリはプロセスで 1 つなので、場面ごとに切り替える。切り替える処理は 1 か所に集めるのがよい（チェケラはパッド・録音用と Intent 用の 2 か所に分かれている）。

| 場面 | カテゴリ | 理由 |
|---|---|---|
| アプリ内で効果音・パッドを鳴らす | `.ambient` | 消音スイッチで鳴らない。ほかのアプリの音楽を止めない `[Apple]` |
| Siri・ショートカットから鳴らす | `.playback`（`.mixWithOthers`） | `.ambient` のままだと消音スイッチで無音になり、Intent は成功したのに何も聞こえない `[Apple]` |
| 録音 | `.playAndRecord`（`.defaultToSpeaker`） | 付けないと受話口から鳴る `[Apple]` |

- 一時的に切り替えたら、**切り替える前のカテゴリとオプションを保存して戻す**。録音パネルを開いたまま Intent が鳴ると、
  戻す先は `.ambient` ではなく `.playAndRecord`
- 重なった呼び出し（Intent の再生中にもう 1 回）では、**最後の呼び出しだけが戻す**。世代番号で判定しないと、
  先の呼び出しが終わった時点で後の音を鳴らしたままカテゴリが戻る
- Intent の経路では `setCategory` / `setActive` の失敗を握りつぶさずエラーにする。`try?` にすると「鳴らないのに成功」になる
  （チェケラのパッド側は `try?` のまま。アプリ内なら鳴らないことに本人が気づける）
- シミュレータには消音スイッチが無いので、テストではカテゴリの値で確かめる（チェケラのベンチはそうしている）

## App Intents から鳴らす

- `perform()` は**鳴り終わるまで待ってから返す**（上限を付ける。チェケラは 30 秒）。返った時点でプロセスが止まりうるのと、
  Siri の画面が音の長さだけ出ている方が自然なため
- `UIBackgroundModes` の `audio` が無いと、背面で起こされたプロセスはセッションを始められない前提で考える `[inferred]`（実機の Siri での確認はまだ）。
  ほかに背面で音を出す理由が無いなら、`audio` を足さずに `supportedModes = .foreground(.immediate)` にする
- アプリ内のパッドは `Button(intent:)` にしない。Intent の経路は遅く、パッドは準備済みの player を直接鳴らす。
  ファイルの解決（ID → URL）だけを Intent と共有する。`app-intents-centric-design` の「UI も `Button(intent:)`」の例外として、
  理由を AGENTS.md か docs に書いておく

## 押した瞬間に鳴らす（遅れ）

計測はシミュレータ（iPhone 17 Pro / iOS 27.2）。実機の値ではないので、前後の比較にだけ使う。手順は `autonomous-perf-loop`、
台帳は CheckItOut の `docs/perf/ledger.md`。

- SwiftUI の `Button` は**指を離したときに**動くので、遅れに押している時間がまるごと入る。0.08 秒押すベンチでは、116.9 ms のうち約 83 ms がこれだった `[measured]`（2026-11、シミュレータ）
- `DragGesture(minimumDistance: 0)` は触れた瞬間の合図にならない。指を離す直前（約 85 ms 後）まで発火しなかった `[measured]`。
  触れた瞬間が要るなら `UIGestureRecognizerRepresentable` で `touchesBegan` から始まる認識器を作る（30.2 ms まで縮んだ）
- 離したときに鳴る方がふつうの使い勝手（ずらすと取り消せる）。触れた瞬間に鳴らすのは**設定で選べるようにし、既定はオフ**にした（ユーザーの判断）。
  オンでも VoiceOver では `.isButton` の要素にして、ダブルタップで鳴るようにする（ダブルタップで鳴るかは実機で未確認）。編集など取り消せた方がよい操作は離したときのまま
- 鳴っている `AVAudioPlayer` を鳴らし直すと、`stop()` でも `currentTime = 0` でも約 10 ms 余計にかかる。準備済みで止まっている player は速い。
  連打する音は**1 つの音に 2 つの player を持ち、止まっている方を鳴らす**。鳴っていた方は新しい音が鳴り始めたあとに止め、頭に戻して準備し直す。
  鳴り直しは約 17 → 5〜7 ms になった `[measured]`
- `AVAudioEngine` + `AVAudioPlayerNode` への切り替えは保留にした（却下ではない）。理由は 2 つ:
  - 計測が信用できなかった。ノードを常に無音で鳴らしておく形だと、音を一切鳴らさない候補でもベンチに合格する作りだった（ベンチのレビューでの指摘）。
    採るなら先に計測を出力のタップから取る（`autonomous-perf-loop` の bench-harness.md）
  - アプリ側のレビューで止める指摘が出た `[inferred]`（コードを読んでの指摘。実機で落としてはいない）:
    `engine.start()` が失敗したまま（通話中・メディアサービスのリセット直後）ノードの `play()` を呼ぶと例外で落ちる、
    割り込みとメディアのリセットでエンジンを作り直す処理が要る、前面にいる間エンジンが無音を描画し続ける（電池）

## AVAudioEngine で鳴らす（月屏風）

手続き合成の BGM を `AVAudioEngine` で鳴らしたとき、実機で鳴らなかったこと。

- **形式はセッションのサンプルレートに合わせる**。`AVAudioUnitReverb` はレートを変換しないので、形式を省くと既定の 44.1kHz になり、
  48kHz の実機で `engine.start()` が `-10868` で失敗した `[measured]`（2026-10、実機）。セッションを有効にしたあとの
  `AVAudioSession.sharedInstance().sampleRate`（取れなければ `outputNode` の形式）で作る
- リバーブはモノラル入力を受け付けない（`-10868`）。2ch で作る
- `setActive(true)` はメインスレッドを塞ぐので裏のスレッド（`Task.detached`）で呼ぶ。非同期の `activate` は
  実機で鳴らなかった原因の候補なので使わず、実績のある同期の `setActive` を裏で呼ぶ形に戻した
- 鳴らし直すたびにセッションを落とさない。毎回 deactivate すると経路の変化が通知され、再起動が連鎖しうる
- 失敗したら、エンジンから組み直す（古いノードを残さない）。どの段階（session / configure / start）と形式で止まったかを
  隠した開発用パネルに出すと、実機で Console なしに原因が見える
- 利用者が自分でオンにした音なら `.playback` + `.mixWithOthers`（消音スイッチで止めない、他アプリの音と混ぜる）。既定はオフにする

## 録音

- 録音のファイル名は UUID にし、保存するのは **Documents からの相対パス**。絶対パスを保存すると、再インストールや更新でコンテナのパスが変わって全部読めなくなる `[measured]`（旧版のバグ）
- 録音のモードを抜けたら（パネルを閉じる・モードを切り替える）入力のタップを外してエンジンを止める。録音の途中で抜けると動いたまま残った `[measured]`
- 保存に成功したらパネルを閉じ、成功の触覚を返す。失敗したらパネルと入力した名前を残す（開いたままだと何も起きなかったように見える）
- マイクの使用目的の文言は具体例まで書く（→ [release.md](release.md) の「審査で落ちた例」）

## 同梱する音源

Debug だけで使うサンプル音源は Release のバンドルに入れない。シードを `#if DEBUG` で囲むだけだとファイルは Release にも同梱される。
外し方と確かめ方は [verification.md](verification.md) の「Release に残さないもの」。
