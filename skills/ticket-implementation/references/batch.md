## バッチモード

複数のチケット URL をスペース区切りで渡すと、依存関係を分析して並列 or 直列で処理する。

### 実行戦略

- **独立チケット** (依存関係なし) → 分離した worktree を使う。独立した十分な規模の作業で、並列エージェントが利用・許可されている場合だけ並列実行し、それ以外は逐次実行
  - 必要な設定はプロジェクトの開発環境手順に従って用意する。`.env` を自動で共有するリンクは張らない。
- **依存チケット** → 直列処理し、先行ブランチを起点にチェーン
  - 例: チケット A → B (A の変更に依存)
    - A: main → branch-a → PR-A (base: main)
    - B: branch-a → branch-b → PR-B (base: branch-a)

### 依存判定

- B の要件が A の変更結果を前提としている
- 同じファイルを変更するだけなら作業の競合であり、仕様上の依存とは別に扱う。競合回避のため逐次実行しても PR の base を不要にチェーンしない
- チケット本文 / コメントで明示的に順序が指定されている

判断が難しければユーザー確認。

### エラーハンドリング

- 1 つのチケットが失敗しても残りは続行
- 依存チェーンで先行が失敗したら後続もスキップ
- 全完了後、結果をまとめて報告

## 親チケット

サブアイテムを持つ親チケットが渡された場合:

1. 親のサブアイテムを取得 (Notion `relation` プロパティ / Linear sub-issues / GitHub task list)
2. 各サブのステータス確認
3. 未着手・着手中のサブを一覧表示
4. 全体対応が依頼済みなら対象サブを実行。対象が不明な場合だけ選択を求める

```
親チケット <ID> のサブチケット:
- [ ] <ID-1>: <タイトル>（未着手）
- [x] <ID-2>: <タイトル>（完了）
- [ ] <ID-3>: <タイトル>（未着手）

どのサブチケットを処理しますか？（スペース区切りで番号、または all で全未着手を処理）
```

親チケット全体・全サブの実装がすでに依頼されていれば、その範囲を再確認しない。親が単なる管理用コンテナで対象が不明な場合だけ選択を求める。
