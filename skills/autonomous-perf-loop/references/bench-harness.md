# 計測の土台の作り方

SKILL.md の Step 0 の正本。実例は touyou/graphica の `scripts/bench/`
（`seed.ts` / `run.ts` / `profile.ts` / `expected.json`）と `docs/process/perf-loop.md`
（読めない環境では、この文書だけで足りるように書いてある）。

## 0. 本番に向かないようにする（最初に作る）

計測用の削除・投入・負荷は、向け先を間違えると本番のデータを消し、無料枠や課金を削る。
人の注意に頼らず、スクリプトで止める。

- 負荷と整合性チェックのスクリプトは、向け先のホストが `127.0.0.1` / `localhost` でなければ
  **起動時に終了する**。検証環境に向けるときだけ、明示のフラグ（`--allow-host <host>`）で許す
- データの投入コマンドにはローカル指定を固定で書く（`wrangler d1 execute <db> --local` など）
- Cloudflare では次がどれも**本番のリソース**につながる: `wrangler dev --remote`、
  `wrangler.jsonc` の binding に `remote: true`、`--local` を付けない `wrangler d1 execute`。
  計測の手順書に「使わない」と書き、実行前に設定を確かめる
- ほかのスタックでも、接続文字列を `.env` から読むなら、計測用の設定ファイルを分けて本番の値が入らないようにする

## 1. 計測用データ

- **固定シードの乱数**で作る。何度作っても同じデータになり、前後比較がデータの違いでぶれない
- 量は「本番の数か月後」を想定する。少なすぎると全件走査が速く見えてしまい、インデックスの問題が出ない
- 偏りも入れる（人気作品にアクセスやいいねが集中する、など）。現実の分布に近いほど、効く改善を選べる
- **見えてはいけないデータを必ず入れる**: 非公開の行、凍結・削除済みのユーザー、他人の非公開データ。
  これが無いと、可視性の条件を壊す変更が整合性チェックを通ってしまう
- 計測用の行は接頭辞（`bench-` など）で区別し、投入前に消してから入れる（何度でもやり直せるように）。
  この削除があるので、0 節の守りを必ず先に入れる

## 2. 点数

1 つの数字にする。複数の数字を並べると、エージェントが都合のよい方を見る。

- 例: 一定時間・一定の並列数で叩いた、**成功したリクエストの 1 秒あたりの数**
- **整合性チェックに 1 つでも落ちたら 0 点**。5xx が 1 件でも出たら 0 点
- 本番の比率を見立てたシナリオの重みを付ける（一覧と詳細が大半、など）。重みはスクリプトの定数にして、
  実際のアクセス比率が分かったら合わせる
- キャッシュがある系では、**既定はキャッシュを外して測る**（URL に乱数のクエリを足す）。
  本番のエッジキャッシュは拠点ごとに別で、アクセスが少ないうちは外れることの方が多い。
  キャッシュありの数字は `--warm` のような別モードで出す

## 3. 整合性チェック

点数より大事。ここが甘いと、ループは壊れた変更を採用し続ける。

| 種類 | 中身 | 例 |
|---|---|---|
| API の中身 | レスポンス本文のハッシュを期待値と比べる | 一覧・詳細・ユーザー情報 |
| ページの中身 | HTML に決まった文字列（タイトルなど）が含まれるか | 作品ページ・ユーザーページ |
| 見えてはいけないもの | 404 / 401 / 403 になること | 非公開の作品、凍結ユーザー、未ログインで自分用 API |
| 人ごとの応答が混ざらない | ユーザー A でリクエストした直後に、未ログインとユーザー B で同じ URL を叩き、A の情報（名前・いいね状態など）が出ないこと | 作品ページ、マイページ、ヘッダー |

最後の行は、計測用のセッション（テスト用ユーザーのログイン Cookie をローカルで発行するなど）が作れるときに入れる。
作れないときは、その穴を手順書に書き、セキュリティだけのレビューで共有キャッシュを重点的に見させる。

だまされないための注意（graphica のレビューで実際に見つかった穴）:

- **確認のリクエストもキャッシュを外す**。前回の正しい本文がキャッシュに残っていると、壊れたビルドでも通る
- **計測用データの範囲だけを見る**。ローカルで後から足した行で期待値がずれると、正しいのに 0 点になる
  （カーソルの範囲を計測用データに限る、など）
- 期待値の記録し直し（`--record`）は、レスポンスの中身を意図して変えたときだけ。ルールとして手順書に書く
  （扱いは下の「レスポンスの中身が変わる変更」）
- 誤検出（正しいのに落ちる）も見逃し（壊れているのに通る）も、どちらもループを狂わせる

### フロントエンド（Lighthouse など）の整合性チェック

性能の点数を上げるために、a11y や SEO を削る変更（画像の alt を消す、見出しを外す）が通らないようにする。

- 守るのは**落ちている項目とその件数**（例: `{"color-contrast": 35, "image-redundant-alt": 17}`）。
  増えたら 0 点。**カテゴリの点数で守らない**。合格していた項目が「対象外」になるだけで点数が下がる
  （iframe を消すと frame-title が消えて a11y が 90→89、など）。良くも悪くもなっていない変更が 0 点になる
- ページの本文に必ず出る文字列も確かめる（白いページで点数を取らせない）
- 本文の確認（fetch）は Lighthouse を回す**前に**まとめて済ませる。後に回すと keep-alive の接続が切れていて落ちる

### レスポンスの中身が変わる変更

列を減らす・形を変える・埋め込みを外す変更は、ハッシュが変わって 0 点になる。次のように扱う。

- 記録し直す前に、変更前と変更後のレスポンスの差分を取り、PR の説明に「レスポンスが変わる点」として載せる。
  セキュリティだけのレビューにも同じ差分を渡す
- 差分が「使っていない項目を減らす」「順序が変わる」だけなら、記録し直して進めてよい
- クライアント（アプリ・別のサービス）が使っている項目を消す・意味を変えるなら、人に確認する
- 見えてはいけないもの（404 / 401）の期待値は、どんな理由でも記録し直さない

## 4. 補助の指標

点数の下で、ボトルネックの当たりを付けるための数字。採用の判断にも使う（SKILL.md の Step 4）。

- **DB の呼び出し回数と時間 / リクエスト**: 無料枠・課金が「読んだ行数」や「クエリ数」で決まる
  サービス（Cloudflare D1 など）では、これが本当の目的になることがある
- **シナリオごとの p50 / p95**: どのページ・API が重いか
- 取り方の例:
  - Cloudflare `wrangler dev`: ローカルのトレース
    （`POST /cdn-cgi/local/explorer/api/local/observability/query` に SQL。`spans` テーブルに
    `trace_id` / `parent_id` / `name` / `duration_ms`。D1 は `name` が `d1_*`）
  - そのほか: ORM のクエリログ、APM のローカル版、DB の slow query log

取れない環境でも点数は出す（補助の指標だけ null にする）。指標の取得でスクリプトを落とさない。

## 5. 出力の形

1 回の計測を JSON 1 つで出す。`scripts/compare.py` はこの形を読む。

```json
{
  "score": 54.2,
  "valid": true,
  "failures": [],
  "rps": 54.2,
  "p50_ms": 102,
  "p95_ms": 319,
  "d1_queries_per_req": 2.18,
  "d1_ms_per_req": 27.94,
  "scenarios": { "page:top": { "n": 120, "p50": 259, "p95": 410 } }
}
```

`score`（数値）/ `valid`（true / false）/ `failures`（文字列の配列）は必須。整合性チェックに落ちたら
`valid: false` と `score: 0` を両方出す。そのほかの数値は任意で、`compare.py` は入れ子のものも含めて
数値のキーを全部並べる。キーの末尾が `_ms` / `_per_req` / `p50` / `p95` / `p99` / `errors` / `_kb` / `_bytes` / `cls` / `_count` のものは
小さいほど良い指標として扱う（それ以外は大きいほど良い）。新しい指標の名前は、この規則に合う末尾にする。

## 6. 環境づくりで詰まりやすいところ

- ランタイムの版: スクリプトをネイティブ TS で動かすなら Node 23.6 以上、など。足りなければ
  作業用ディレクトリに入れて PATH を通す（システムのものは触らない）
- `pkill -f "<コマンド>"` は、そのコマンド名を含む自分のシェルまで止めることがある。
  `ps` で PID を絞ってから止める
- ローカル DB にファイルで SQL を流すとき、トランザクション文（`BEGIN` / `COMMIT`）を受け付けない実装がある（D1）
- **交互に測る**: 基準（元のコミットを `git worktree` でビルドしたもの）と候補を別のポートで同時に立て、
  基準 → 候補 → 基準…と交互に回す。続けて測ると、その間のマシンの混み具合が片方にだけ乗る。
  worktree では `node_modules` を symlink で共有せず、その中で依存を入れ直す（バンドラがルートを誤認することがある）
- **計測環境から見えないもの**を先に書き出す。プロキシなどで外部（動画の埋め込み・広告・解析）への通信が止まると、
  本番で一番重い部分が点数に出ない。外部への通信の件数（`ext_req_count`）などの代わりの指標を出し、PR にも書く
- ビルドの型チェックが `scripts/` も対象にしていることがある。トップレベル await を使うスクリプトは
  `export {}` で module にし、`Node` や `self` などのグローバル名と衝突させない

## 7. 整合性チェックをだませないかのレビュー

土台を作ったら 1 回、チェックを変えたらそのたびに、別のエージェントに頼む。作った側の考え（なぜ穴が無いと思うか）は渡さない。

```text
You are reviewing the integrity checks of a local benchmark in <repo> (<bench script path>). The
benchmark gives a score only when every check passes. Your job is to find ways a broken or unsafe
change could still pass the checks, and ways a correct change could fail them. Do not modify files.

Think like an agent that wants a higher score: what could it change in the app so that the checks
still pass while responses are wrong, empty, stale, or visible to the wrong user? Consider caches
(including the check requests themselves hitting a cache), data added outside the seed, hidden or
suspended rows, per-user responses, error pages that return 200, and where the script sends requests.

Report every finding, including low-confidence ones, with file:line, a concrete scenario, and a
confidence label (high/medium/low). Keep it concise.
```

指摘は全部読む。直すか、直さない理由を手順書に書く。確度の低い指摘も捨てない。
