## 0. 本番に向かないようにする（最初に作る）

計測用の削除・投入・負荷は、向け先を間違えると本番のデータを消し、無料枠や課金を削る。
人の注意に頼らず、スクリプトで止める。

- 負荷と整合性チェックのスクリプトは、向け先のホストが `127.0.0.1` / `localhost` でなければ
  **起動時に終了する**。検証環境に向けるときだけ、明示のフラグ（`--allow-host <host>`）で許す
- データの投入コマンドにはローカル指定を固定で書く（`wrangler d1 execute <db> --local` など）
- Cloudflare では次がどれも**本番のリソース**につながる: `wrangler dev --remote`、
  `wrangler.jsonc` の binding に `remote: true`、`--local` を付けない `wrangler d1 execute`。
  計測の手順書に「使わない」と書き、実行前に設定を確かめる
- ほかのスタックでも、接続文字列を `.env` から読むなら、計測用の設定ファイルを分けて本番の値が入らないようにする
- 向け先の無い計測（オフラインの描画や CLI）では、この節の守りは要らない。代わりに、計測環境が本番と別物
  （Mac の GPU で測るが本番は別の端末、など）なら「絶対値は使わず、前後の比較にだけ使う」と手順書に書く

## 1. 計測用データ

- **固定シードの乱数**で作る。何度作っても同じデータになり、前後比較がデータの違いでぶれない
- 量は「本番の数か月後」を想定する。少なすぎると全件走査が速く見えてしまい、インデックスの問題が出ない
- 偏りも入れる（人気作品にアクセスやいいねが集中する、など）。現実の分布に近いほど、効く改善を選べる
- **見えてはいけないデータを必ず入れる**: 非公開の行、凍結・削除済みのユーザー、他人の非公開データ。
  これが無いと、可視性の条件を壊す変更が整合性チェックを通ってしまう
- 計測用の行は接頭辞（`bench-` など）で区別し、投入前に消してから入れる（何度でもやり直せるように）。
  この削除があるので、0 節の守りを必ず先に入れる

## 2. 点数

1 つの数字にする。複数の数字を並べると、エージェントが都合のよい方を見る。

- 例: 一定時間・一定の並列数で叩いた、**成功したリクエストの 1 秒あたりの数**
- **整合性チェックに 1 つでも落ちたら 0 点**。5xx が 1 件でも出たら 0 点
- 本番の比率を見立てたシナリオの重みを付ける（一覧と詳細が大半、など）。重みはスクリプトの定数にして、
  実際のアクセス比率が分かったら合わせる
- キャッシュがある系では、**既定はキャッシュを外して測る**（URL に乱数のクエリを足す）。
  本番のエッジキャッシュは拠点ごとに別で、アクセスが少ないうちは外れることの方が多い。
  キャッシュありの数字は `--warm` のような別モードで出す

## 3. 整合性チェック

点数より大事。ここが甘いと、ループは壊れた変更を採用し続ける。

| 種類 | 中身 | 例 |
|---|---|---|
| API の中身 | レスポンス本文のハッシュを期待値と比べる | 一覧・詳細・ユーザー情報 |
| ページの中身 | HTML に決まった文字列（タイトルなど）が含まれるか | 作品ページ・ユーザーページ |
| 見えてはいけないもの | 404 / 401 / 403 になること | 非公開の作品、凍結ユーザー、未ログインで自分用 API |
| 人ごとの応答が混ざらない | ユーザー A でリクエストした直後に、未ログインとユーザー B で同じ URL を叩き、A の情報（名前・いいね状態など）が出ないこと | 作品ページ、マイページ、ヘッダー |

最後の行は、計測用のセッション（テスト用ユーザーのログイン Cookie をローカルで発行するなど）が作れるときに入れる。
作れないときは、その穴を手順書に書き、セキュリティだけのレビューで共有キャッシュを重点的に見させる。

だまされないための注意（graphica のレビューで実際に見つかった穴）:

- **確認のリクエストもキャッシュを外す**。前回の正しい本文がキャッシュに残っていると、壊れたビルドでも通る
- **計測用データの範囲だけを見る**。ローカルで後から足した行で期待値がずれると、正しいのに 0 点になる
  （カーソルの範囲を計測用データに限る、など）
- 期待値の記録し直し（`--record`）は、レスポンスの中身を意図して変えたときだけ。ルールとして手順書に書く
  （扱いは下の「レスポンスの中身が変わる変更」）
- 誤検出（正しいのに落ちる）も見逃し（壊れているのに通る）も、どちらもループを狂わせる
- **チェックが空振りしないことを確かめる**。計測用データに対象の行が無いと、可視性のチェックが何も見ずに通る
  （実例のアプリでは最初リアクションが 0 件で、一覧の API は常に空の配列を返していた）。件数の下限
  （「50 件以上返ること」）と、「見える人には出る」側のチェックも入れる。見えない人に出ないことだけを見ると、
  何も返さない候補が通る
- **計測とチェックのコードは基準の側のものを使う**。候補の checkout がベンチやチェッカー自身を持っていると、
  それを書き換えた変更が通る。候補をビルドするときに計測用のディレクトリを基準のものに差し替える、
  期待値を checkout の外に置く、計測スクリプトは基準の worktree から動かす（Tsukibyobu のレビューで見つかった一番大きな穴）
- **計測対象の自己申告で仕分けない**。「キャッシュに当たったか」「焼き直したか」を対象の戻り値やヘッダーで仕分けると、
  空の組が 0ms と数えられて点数が上がる。仕分けた件数が想定と違えば不合格にする
- **計測の経路と本番の経路を揃える**。計測用の入口（オフスクリーンの書き出し、計測用の API）だけ正しく、
  本番の経路では違う、という変更を落とすため、チェックは本番と同じ経路でも流す

### フロントエンド（Lighthouse など）の整合性チェック

性能の点数を上げるために、a11y や SEO を削る変更（画像の alt を消す、見出しを外す）が通らないようにする。

- 守るのは**落ちている項目とその件数**（例: `{"color-contrast": 35, "image-redundant-alt": 17}`）。
  増えたら 0 点。**カテゴリの点数で守らない**。合格していた項目が「対象外」になるだけで点数が下がる
  （iframe を消すと frame-title が消えて a11y が 90→89、など）。良くも悪くもなっていない変更が 0 点になる
- ページの本文に必ず出る文字列も確かめる（白いページで点数を取らせない）
- 本文の確認（fetch）は Lighthouse を回す**前に**まとめて済ませる。後に回すと keep-alive の接続が切れていて落ちる

### レスポンスの中身が変わる変更

列を減らす・形を変える・埋め込みを外す変更は、ハッシュが変わって 0 点になる。次のように扱う。

- 記録し直す前に、変更前と変更後のレスポンスの差分を取り、PR の説明に「レスポンスが変わる点」として載せる。
  セキュリティだけのレビューにも同じ差分を渡す
- 差分が「使っていない項目を減らす」「順序が変わる」だけなら、記録し直して進めてよい
- クライアント（アプリ・別のサービス）が使っている項目を消す・意味を変えるなら、人に確認する
- 見えてはいけないもの（404 / 401）の期待値は、どんな理由でも記録し直さない

## 4. 補助の指標

点数の下で、ボトルネックの当たりを付けるための数字。採用の判断にも使う（SKILL.md の Step 4）。

- **DB の呼び出し回数と時間 / リクエスト**: 無料枠・課金が「読んだ行数」や「クエリ数」で決まる
  サービス（Cloudflare D1 など）では、これが本当の目的になることがある
- **シナリオごとの p50 / p95**: どのページ・API が重いか
- 取り方の例:
  - Cloudflare `wrangler dev`: ローカルのトレース
    （`POST /cdn-cgi/local/explorer/api/local/observability/query` に SQL。`spans` テーブルに
    `trace_id` / `parent_id` / `name` / `duration_ms`。D1 は `name` が `d1_*`）
  - そのほか: ORM のクエリログ、APM のローカル版、DB の slow query log

- **サーバーの CPU 時間 / リクエスト**: 計測の前後で、リクエストを実際に処理するプロセスの CPU 時間を読み、成功数で割る
  （`wrangler dev` なら node の wrangler ではなく子の `workerd`。2 つあるうち負荷で CPU を使う方）。
  Linux は `/proc/<pid>/stat` の 14・15 番目（utime / stime）を `getconf CLK_TCK`（多くの環境で 100 = 10ms）で割る。
  2 番目の名前に空白や `)` が入りうるので、最後の `)` の後ろで区切る
- **頭打ちの要因の確かめ方**: 並列を 1・2・4・8… と上げて、点数がどこで伸びなくなるか、そのときのサーバーの CPU 使用率と、
  負荷をかける側の使用率を見る。サーバーの 1 コアがほぼ埋まり、点数が「1 ÷ CPU 時間 / リクエスト」の近くで止まるなら CPU で決まっている
  （実例の `wrangler dev` は 1 スレッドで、点数 ≈ 920 ÷ CPU ms。使用率が 9 割強だったため）。このとき `p50` や DB の時間の多くは順番待ちで、
  待ちを減らす変更（DB の呼び出しを並べるなど）は点数に出ない。呼び出し回数・読み取り行数・待ちの段数で評価する
- **DB の読み取り行数 / リクエスト**: `wrangler dev`（workerd 1.2026 系で確認）のトレースでは、D1 の span の `attributes` に
  `cloudflare.d1.response.rows_read` が入る（`json_extract` で合計する）。「取れない」と台帳に書いた指標も、環境を上げたら見直す。
  行数は別のクエリで引き、それが失敗しても呼び出し回数などは残す（行数だけ null にする）

取れない環境でも点数は出す（補助の指標だけ null にする）。指標の取得でスクリプトを落とさない。

**採否に使う補助の指標を Step 0 で決めて手順書に書く**。OS が数える値（プロセスのメモリのピークなど）は、
計測のループそのもの（連続描画、長く動いたサーバー）に引きずられてぶれが大きい。何を数えているかを確かめ、
使わないなら「参考」と書いておく（その場の都合で、採用の根拠にしたりしなかったりしない）。

### 一斉アクセス（スパイク）のシナリオ

「全社会で全員が同時にホームを開く」ような山は、1 本ずつの速さとは別に測る。

- **画面を開いたときの API をブラウザで一度記録して、読み取りの要求だけを再生する**（Playwright で `request` を拾う）。
  手で選んだ API だけだと、画面が同じ一覧を何度も取り直しているような無駄に気づけない。
  POST など状態を変える要求は再生しない（計測用データが変わる）。ログインが要る要求は、人ごとに計測用のセッションを作って差し替え、
  記録したときの Cookie・`Authorization`・人や組織の ID を N 人で使い回さない（1 人分の負荷を N 回測ることになる）
- 点数は「N 人が同時に開いて、画面が揃うまでの p95」と、エラーの数
- **開発用のサーバーで測ると、開発用の重さを測ってしまう**。実例のアプリでは `next dev` の CPU が 100% になり、
  CPU プロファイル（`kill -USR1 <pid>` で inspector を開き、CDP の `Profiler`）の大半は開発用の処理だった。
  本番用のビルドで測れないか先に確かめる（実例のアプリはローカルのログインが開発モードでしか使えず、できなかった）
- 本番の構成で何が先に詰まるかを考えて、指標を選ぶ。サーバーが横に増える構成（Cloudflare Workers など）なら、
  詰まるのは DB。**1 回開くあたりの DB の実行時間の合計**（PostgreSQL なら `pg_stat_statements` を空にしてから 1 回開く）を見る。
  `pg_stat_statements` は要求ごとに分かれないので、ヘルスチェックや別のタブなど計測対象外の要求が混ざった回は使わない

## 5. 出力の形

1 回の計測を JSON 1 つで出す。`scripts/compare.py` はこの形を読む。

```json
{
  "score": 54.2,
  "valid": true,
  "failures": [],
  "rps": 54.2,
  "p50_ms": 102,
  "p95_ms": 319,
  "d1_queries_per_req": 2.18,
  "d1_ms_per_req": 27.94,
  "scenarios": { "page:top": { "n": 120, "p50": 259, "p95": 410 } }
}
```

`score`（数値）/ `valid`（true / false）/ `failures`（文字列の配列）は必須。整合性チェックに落ちたら
`valid: false` と `score: 0` を両方出す。そのほかの数値は任意で、`compare.py` は入れ子のものも含めて
数値のキーを全部並べる。キーの末尾が `_ms` / `_per_req` / `p50` / `p95` / `p99` / `errors` / `_kb` / `_bytes` / `cls` / `_count` のものは
小さいほど良い指標として扱う（それ以外は大きいほど良い）。`p90` も同じ。新しい指標の名前は、この規則に合う末尾にする。

同じビルド同士のぶれがほぼ 0 の計測（GPU の実行時間など）では、`-0.03%` でも「悪化」と判定される。
`compare.py --noise-floor 1` のように、ぶれの下限を手順書で決めて渡す。

## 6. 環境づくりで詰まりやすいところ

- **大きな転送・複製は、小さく試して大きさを確かめてから**。範囲指定（`curl -r` など）が相手に無視されると、
  先頭だけのつもりが丸ごと落ちてくる（ISUCON2026 では先頭 200MB のつもりが 13GB をダウンロードした）。
  先に 1 件・小さい範囲で試して受け取った大きさを見る。ディスクの空きを予算として状態に書いておく
- ランタイムの版: スクリプトをネイティブ TS で動かすなら Node 23.6 以上、など。足りなければ
  作業用ディレクトリに入れて PATH を通す（システムのものは触らない）
- `pkill -f "<コマンド>"` や `pgrep -f "<コマンド>" | xargs kill` は、そのコマンド名を含む自分のシェルまで止めることがある。
  ポートで探す（`lsof -ti :<port>`）か、`ps` で PID を絞ってから止める
- **計測用データを作り直す手順を 1 本のスクリプトにする**。結合テストが DB の中身を入れ替えるリポジトリでは、
  テストを流すたびに計測用データが消える。投入・計測用の行の追加・設定（組織の slug など）までを 1 回で戻せるようにし、
  できれば計測用とテスト用で DB を分ける（PostgreSQL のロールはクラスタ全体のものなので、DB を分けてもマイグレーションが
  ロールの作成で落ちることがある。そのときはコンテナごと分ける）
- **混ぜて測るときの干渉**: 1 プロセスの開発サーバーに並列で投げると、重いシナリオが速くなっただけで、ほかのシナリオの待ちも変わる
  （`compare.py` が「変更していないシナリオも動いた」と出す）。そのときは、変更していないシナリオだけを並列 1 で
  基準と候補の両方で測り、ぶれの範囲に収まることを確かめてから採用の根拠を書く
- **計測中は、テスト・ビルド・別の計測を裏で流さない**。CPU を取り合って、その回だけ数字が荒れる（実例のアプリでは 1 回それで
  p95 が 3 割悪く出た）。裏の仕事を待ってから測る。
  捨ててよいのは、その回に裏の仕事が動いていたこと（CPU 使用率・動いていたプロセス）を確かめられた回だけ。数字が悪いだけで捨てると、
  本当の悪化をノイズとして見逃す。捨てるときは基準と候補の両方を同じ手順で測り直し、元の JSON は上書きせずに残す
- **コンテナが作り直されることがある**。手元の DB・dockerd・開発サーバーを立ち上げ直す手順も、データを入れ直すスクリプトと
  一緒に書いておく（作業用ディレクトリのファイルは残っても、プロセスは消える）
- ローカル DB にファイルで SQL を流すとき、トランザクション文（`BEGIN` / `COMMIT`）を受け付けない実装がある（D1）
- **コンテナのイメージが取れない環境**（クラウドの作業環境でレジストリへの通信が止まっているなど）では、
  入っているネイティブの PostgreSQL を使う。リポジトリに「素の PostgreSQL へ当てる」経路（ホスティング先の機能を
  抜いた bootstrap とマイグレーション）があればそれで作る。将来の移行先（別のマネージド PostgreSQL など）と
  同じ経路なので、その移行の後も効くかを同時に確かめられる
- サーバーを立てずに、テスト用の認証の抜け道（テストランナーの中だけで効くヘッダーなど）を使って、
  アプリの関数をプロセスの中から呼ぶ（Hono の `app.request()` など）と、ネットワークとサーバーのぶれが乗らない。
  テストランナーが標準出力を隠すことがあるので、結果はファイルに書く
- **計測のコードはリポジトリの作業ツリーの外に置き、測るときだけ持ち込む**。追跡していないファイルでも、
  push 前の lint が拾って落ちることがある
- **交互に測る**: 基準（元のコミットを `git worktree` でビルドしたもの）と候補を別のポートで同時に立て、
  A B → B A → A B…と順番も入れ替えながら回し、組ごとの比（候補 ÷ 基準）を取る。続けて測ると、その間のマシンの混み具合や、
  サーバーを立ててからの時間（実例では立ち上げ直後 46 点、10 分後 50〜56 点）が片方にだけ乗る
  - **先に A/A**: 同じコードどうしで回し、比の範囲を出す（実例の共有のクラウド環境では、10 秒ずつ 6 組で点数の比 0.97〜1.10、
    CPU の比 0.93〜1.02）。範囲の真ん中が 1 からずれていたら、ポートや立てた順の偏りなので、A と B を入れ替えて測り直す
  - **判定**: 組ごとの比の中央値が A/A の範囲の外にあり、組の過半で同じ向きなら、点数で採否を決めてよい。範囲の中なら
    `compare.py` の「ぶれの範囲」（終了コード 2）と同じ扱いで、補助の指標で決める。`compare.py` にも A 側の JSON を `--base`、
    B 側を `--cand` に渡し、整合性チェックの失敗・0 点の判定はそちらで通す。`--noise-floor` と `plateau.py --noise` には、
    A/A の範囲の 1 から遠い側（0.97〜1.10 なら 10）を % で渡す。時系列には A 側を `base`、B 側を `cand` として書く
  - 候補の側が整合性チェックに落ちた組があれば差し戻し。基準の側が落ちたら、環境か土台の問題なので、直してから測り直す
  worktree では `node_modules` を symlink で共有せず、その中で依存を入れ直す（バンドラがルートを誤認することがある）
- **計測環境だけの重さ**: 開発用のサーバーが応答を圧縮する（本番では edge が圧縮して、アプリの CPU に乗らない）など。
  外すなら比較の両側で同じ設定にし、既定の点数を変えるなら人に確認する
- **計測環境から見えないもの**を先に書き出す。プロキシなどで外部（動画の埋め込み・広告・解析）への通信が止まると、
  本番で一番重い部分が点数に出ない。外部への通信の件数（`ext_req_count`）などの代わりの指標を出し、PR にも書く
- ビルドの型チェックが `scripts/` も対象にしていることがある。トップレベル await を使うスクリプトは
  `export {}` で module にし、`Node` や `self` などのグローバル名と衝突させない

## 7. 整合性チェックをだませないかのレビュー

土台を作ったら 1 回、チェックを変えたらそのたびに、別のエージェントに頼む。作った側の考え（なぜ穴が無いと思うか）は渡さない。

```text
You are reviewing the integrity checks of a local benchmark in <repo> (<bench script path>). The
benchmark gives a score only when every check passes. Your job is to find ways a broken or unsafe
change could still pass the checks, and ways a correct change could fail them. Do not modify files.

Think like an agent that wants a higher score: what could it change in the app so that the checks
still pass while responses are wrong, empty, stale, or visible to the wrong user? Consider caches
(including the check requests themselves hitting a cache), data added outside the seed, hidden or
suspended rows, per-user responses, error pages that return 200, and where the script sends requests.

Report every finding, including low-confidence ones, with file:line, a concrete scenario, and a
confidence label (high/medium/low). Keep it concise.
```

指摘は全部読む。直すか、直さない理由を手順書に書く。確度の低い指摘も捨てない。

## 8. 描画（GPU）の計測

Tsukibyobu（Metal の 2 パス描画）で使った形。Web の考え方との対応を書く。

- **点数**: フレームの種類ごとの GPU 時間（command buffer の `gpuEndTime - gpuStartTime`）の重み付き平均の逆数。
  重みは「その状態で過ごす時間 × fps」で決める（静止中の毎フレーム、操作中の焼き直し、まれな全体の焼き）。
  Web の「アクセス比率」に当たる
- **壁時計も並べる**: GPU 時間は渡した command buffer の分しか数えないので、仕事を別の command buffer・CPU・
  初期化に逃がすと点数だけ上がる。壁時計と初期化の時間が下がらない候補は差し戻す
- **計測用データ**: 状態（場所・季節・角度・時刻・seed・画面サイズ）の集合。「見えてはいけないデータ」の代わりに、
  **内部キャッシュ（焼きの使い回し）の誤りを落とす並び**を入れる。1 つのレンダラで順に描き、直前と 1 項目だけ
  変えた状態を続ける（Web の「確認のリクエストもキャッシュを外す」に当たる）。ベンチと同じ細かい刻み
  （1/30 秒、1°）も入れる
- **整合性チェック**: 画素の完全一致（RGB のハッシュ）。アプリの書き出し先（`bgra8Unorm`・renderTarget だけ）でも描いて比べる
- **浮動小数の丸め**: 数学的に同じ書き換えでも、分岐の置き場所や関数の分け方だけでコンパイラの最適化（FMA の付き方など）が
  変わり、1 階調ずれることがある。ハッシュやノイズの前後は特に敏感。落ちた案の扱いは SKILL.md の Step 4
- **チェックは標本でしかない**: 「このマスクの外では結果に効かない」を理屈で言い切れない変更は、
  チェックの集合の外の状態も広く（その周だけ 100 前後）比べてから採用する

## 9. アプリの中で測る（iOS など）

チェケラ（サウンドボードの「タップから音が出るまで」）で使った形。計測のプローブがアプリのプロセスの中で動くので、Web や CLI と違う守りが要る。

- **点数**: 入力の時刻（`UITouch.timestamp` と同じ時計）から出力まで。内訳（指を離すまで・処理の呼び出しまで・処理の中・出力の遅れ）を分けて出す。
  出力の時刻を直接取れないときは推定（`outputLatency + ioBufferDuration` など）と台帳に書く。シミュレータの値は前後の比較にだけ使う
- **基準の側のコードで測る**: プローブのファイルは基準のものに差し替えられるが、アプリのコードに入れたフックの行・プロジェクトファイル・
  音源などの素材は差し替えられない。それらの差分を関門にして、触っていたら止める
- **画素のハッシュに当たるものが無い出力**（音など）は、プローブで出力側の状態（どの音源を・頭から・どの音量で鳴らしているか）を読む。
  出力の装置の時計（オーディオエンジンのノードの時刻など）で測ると、無音を流し続けるだけの候補でも進むので、**出力そのもの（出力にタップを付けて音の立ち上がり）**から測る
- **計測のコードを本番に出さない**: プローブは `#if DEBUG` と起動引数の両方で囲み、Release のバイナリにプローブの記号や文字列が無いことをスクリプトで確かめる
  （security-gates.md の「最初に却下する案」）
- UI テストで叩くと、押す長さ・イベント配送の揺れがシミュレータ側に乗る。アプリから動かせない分は台帳に分けて書き、採否は処理の中の時間で裏付ける

### サーバーへのリクエスト数を点数にする（Flutter などのクライアント）

Habee（Flutter、サーバーは変えられない前提）で使った形。点数は「決めた巡回で出る API リクエスト数」で、
debug ビルドのログの要求行を数える（シミュレータ、本番以外の環境）。UI を操作して測るので、次の守りを最初から入れる。

1. **ログを保存する前にトークンを伏せる**。アプリの API ログには `Authorization` ヘッダーが出る。
   巡回のログをファイルに書く処理の先頭に、伏せ字にする処理を入れる（後から消すのでは、途中の写しに残る）
2. **行ごとに受信時刻を付ける**。`flutter run` の出力には時刻が無く、区間の所要時間や、重複した 2 本の時刻差が取れない。
   受け取った側（`ts` や小さなスクリプト）で行ごとに時刻を付ける
3. **「静かになるまで待つ」巡回と「素早く切り替える」巡回を、基準の段階から両方取る**。各画面で 15 秒待つ巡回では、
   10 秒の使い回し期間の効果が見えない（期間が切れてから次の画面に行くため）。3 秒ほどで切り替える巡回を併用して初めて差が出る
4. **基準の段階から区間ごとにスクショを撮る**。「画面の中身が変わっていない」を整合性チェックにするとき、
   基準のスクショが無いと後から並べて比べられない
5. **計測で状態が変わるものは、元に戻す手段を先に用意する**。通知の画面を開くと既読になり、2 回目からは
   「未読のバッジが消えるか」を確かめられない。計測の前に未読を作る手段（テスト用の API・シードなど）を用意する
6. **計測用の checkout は worktree にする**。手元の主 checkout でブランチを切り替えながら測ると、途中で止まったとき
   （Mac がオフラインになった、など）に `index.lock` が残り、作業中の checkout ごと壊れる
7. **外れ値は、ログの時刻で理由を確かめてから捨てる**。UI 操作のタップが 2 回入る、マシンが遅くなって区間が長くなる、
   といった外れ値が出る。3 回取り、外れた回は時刻付きのログで原因を確かめ、理由を台帳に書いてから除く

重複の見分け方は bottleneck-playbook.md の 3 節、間引くときの確認は SKILL.md の Step 4 と「判断の線引き」。
