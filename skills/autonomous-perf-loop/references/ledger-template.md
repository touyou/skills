# 台帳の書き方

会話が要約されて文脈が消えても、台帳を読めば次の周から再開できるようにする。台帳は 2 つに分ける。

| | 置き場所の例 | 書き方 |
|---|---|---|
| **周の記録** | プロジェクトの開発記録（`docs/devlog/YYYY-MM.md`） | 1 周 1 項目で追記。経緯なので過去形で書き、後から書き換えない |
| **状態** | 作業用のファイル（`perf-loop-state.md`。リポジトリに入れない場所でもよい） | 周ごとに上書きする。今の基準・予算・候補の列 |
| **時系列** | 状態の隣（`timeline.jsonl`） | 計測 1 回ごとに 1 行を追記。`scripts/plateau.py` が読む（plateau-audit.md の 1 節） |

## 1 周ぶんの項目

```markdown
## YYYY-MM-DD 性能改善ループ N 周目: <対象> / <ブランチ名>（経過 h:mm〜h:mm）

- **背景**: 前の周で分かったこと、この周で狙うもの
- **判断**:
  - ボトルネックの根拠（どの指標・実行計画・プロファイルで見たか）
  - 変えたこと（1 つ）。意味が変わらないことをどう確かめたか
  - 却下した案と理由（セキュリティの基準に当たったもの、効かなかったもの）
- **結果**（3 回の中央値）: 点数 A → B（±x%、ぶれの範囲か）、補助の指標の前後。採用 / 差し戻しと、
  点数と指標のどちらで決めたか
- **詰まった点 / 学び**: 環境の落とし穴、次の周の候補
- **スキルの手順が合わなかった点**（新しい種類の対象で試すとき）: あとでスキルに戻す
- **確認**: テスト・lint・ビルド、計測の回数、セキュリティだけのレビューの結果
- **停滞の判定**: `plateau.py` の結果（停滞なら、監査をいつ挟んだか）
```

- セキュリティだけのレビューの指摘の件数と、それぞれの扱い（直した / PR の「要確認」に載せた）

## 状態（周ごとに上書き）

```markdown
# 性能改善ループの状態

- 条件: 計測先 <ローカル / 検証環境の名前>、やらないこと <人が指定したもの>、ディスクの空き <使ってよい量>。
  人の指示でだけ書き換える
- 予算: N 周 / H 時間まで（使ったもの: n 周 / h 時間）
- 最後に点数が伸びた時刻と、停滞の監査を挟んだ時刻・そのときの「最後の更新」の時刻（無ければ「なし」）
- 進行中の周: N 周目の Step n、作業ブランチ、まだ採否を決めていない変更（コミットか stash の名前）。
  周の途中でも、Step が進むたびに書き換える
- 計測の手順: <手順書のパス>（採否に使う補助の指標と、ぶれの下限、点数の上限が負荷をかける側で決まっていればそのことも書く）
- 現在の起点: <ブランチかコミット>、点数の中央値 X（ぶれ ±y%）、主な補助の指標
- 開いている PR: <番号と、積んでいるかどうか>
- 次の周の候補（優先順）: 1. … 2. …
- 試して効かなかった案: …（同じ案を二度試さない）
- 却下した案と理由: …（同じ検討を二度させない）
```

新しいセッション、または会話が要約された直後は、まず状態を読み、次に直近の周の記録と `plateau.py` の出力を読む。
「進行中の周」が残っていれば、その周を書いてある Step から終わらせるか、変更を戻して台帳に「中断: 理由」と書いてから
Step 1 に入る。採否を決めていない変更が載ったまま基準を測ると、その変更を確かめずに起点へ取り込んでしまう。
