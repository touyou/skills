# ボトルネックの見つけ方

SKILL.md の Step 2 の正本。「推測より先に測る」。graphica で実際に効いた順に並べている。

## 1. どこが重いかの当たりを付ける

- シナリオごとの p50 を並べる。DB を使わないページが API の何倍遅いかで、DB と描画のどちらが本命か分かる
- 1 リクエストあたりの DB の呼び出し回数と時間を、ページごとに出す（トレースを trace_id でまとめる）。
  呼び出しが多いページ、1 回が重いページを探す
- **読み取りの API を一通り叩き、応答の大きさと時間を並べる**。応答が数十バイトなのに 1 秒かかる API は、
  答えに要らないものを読んでいる（全件を読んでから絞っている）見込みが高い。実例のアプリではタグの候補（674 バイト・1.3 秒）と
  リアクションした文書（12 バイト・1.3 秒）がこれで見つかった
- 答えに要るものが少ないなら、**小さい側から引く**。「全件を読んで本人の分を絞る」より「本人の行（リアクションなど）を先に引き、
  その分だけ見られるかを確かめる」ほうが、全体の件数に引きずられにくくなる場合がある。効くかどうかは実行計画とベンチマークで確かめる
- **サーバーが暇なのに点数が頭打ちなら、負荷をかける側を疑う**。アプリの CPU が 2〜3 割で、サーバーの中の処理時間がほぼ 0 なのに
  伸びないときは、ベンチのクライアントの並列数・CPU・接続の作り方が上限になっていることがある。アプリを削る前に、
  クライアントの側の使用率を見て、状態の「計測の手順」に書く

## 1.5 リポジトリにある道具を先に探す

権限の判定を SQL にした関数や、計測の道具が既にあることがある（実例のアプリには「見られる文書」を SQL で出す関数と、
TypeScript の判定と食い違わないかをランダムに比べるテストがあった）。新しく書くより、それを使い回すほうが安全で速い。
使い回すときも、元の判定と同じ範囲になるか（フォルダ・ゴミ箱・アーカイブなどを含むか）を、呼び出し側の絞り込みと合わせて確かめる

## 2. DB: 実行計画を読む

```sh
# SQLite / D1 の例
npx wrangler d1 execute <db> --local --command "EXPLAIN QUERY PLAN <SQL>"
```

| 実行計画に出るもの | 意味 | よくある直し方 |
|---|---|---|
| `USE TEMP B-TREE FOR ORDER BY`（MySQL は `Using filesort`） | 並べ替えのために条件に合う行を全部読んでいる | `where` の等値条件 → `order by` の列の順の複合インデックス |
| `SCAN <table>` | 全件走査 | 絞り込みの列にインデックス |
| 複合主キーがあるのに `SCAN` | 主キーの 2 番目の列で引いている（先頭の列からしか使えない） | 引く列を先頭にした別のインデックス |
| 別の表にまたがる `OR` で `SCAN` | どちらのインデックスでも両方を拾えない | 片方を先に引き当てる（`coalesce((select ...), :key)` など）か、2 クエリに分ける。意味が変わらないかを先に確かめる |
| `count(*)` が毎回全件 | 件数表示のために全行を読んでいる | 公開・全員共通なら短い期限付きのメモ（security-gates.md の判断表） |

- 「読んだ行数」で課金・無料枠を数える DB（D1 など）では、返す行数ではなく**読む行数**を減らす
- 単体のインデックスを 2 本張っても、1 つのクエリで使われるのは基本 1 本だけ
- 複合インデックスは先頭の列だけの検索にも使える。単体のインデックスが不要になったら消す（書き込みが軽くなる）
- ローカル DB が「読んだ行数」を返さない実装（ローカル D1 など）では、実行計画と、計測用データの
  件数から見積もる

### PostgreSQL の行単位のセキュリティ（RLS）

RLS の policy が関数（`auth.uid()` や「所属している組織の ID」を返す関数など）を素のまま呼んでいると、
**行ごとに評価される**。1 リクエストで数十回同じ関数が走り、DB の時間の大半を占めることがある
（実行計画には出にくい。`pg_stat_statements` を `track = all` にすると、関数の中の文が回数つきで見える）。

- 引数の無い `STABLE` の関数なら、`(select f())` で包むと planner が initPlan として **1 文 1 回**だけ評価する。
  意味は変わらない（[Supabase の RLS 性能の推奨](https://supabase.com/docs/guides/database/postgres/row-level-security#call-functions-with-select)）
- 配列を返す関数は型を付ける: `col = any ((select f())::uuid[])`。付けないと `any (副問い合わせ)` と解釈され、
  `uuid = uuid[]` で落ちる
- policy が多いときは手で書き換えない。**生きている DB の `pg_policies` を `search_path = ''` で逆解析した式**から
  `ALTER POLICY` を機械的に作る（宣言のスキーマにない policy も拾える）。作ったら、包みを外した式が元の式と一致すること、
  roles・cmd・PERMISSIVE が変わらないことを全件で突き合わせる
- 宣言のスキーマとマイグレーションを両方持つリポジトリでは、それぞれから作った DB の `pg_policies` が一致することも確かめる
- 関数が GUC（`request.jwt.claims` など）を読むなら、その値を同じ文の中で書き換えていないか確かめる。
  別の文で立てているなら、1 文 1 回にしても読む値は変わらない

## 3. DB: 要らないクエリを探す

- 汎用の関数を使い回して、**使っていない列のためにクエリを打っていないか**（いいね済みかだけ要るのに、
  いいね数も取る関数を呼んでいる、など）。元の関数は消さず、必要な分だけの関数を足す
- 同じリクエスト内で同じ問い合わせを 2 回していないか（メタデータ生成と本体、など）。
  フレームワークのリクエスト内メモ（React の `cache()` など）でまとめる。`cache()` はリクエストごとに
  捨てられるので共有キャッシュの危険は無いが、失敗した Promise も使い回す（metadata で一度失敗すると
  本体も同じ失敗になる）。Route Handler のように描画の外で呼ぶと何もキャッシュしない
- N+1: 一覧の 1 行ごとにクエリを打っていないか
- **画面が同じ問い合わせを取り直していないか**。API を 1 本ずつ測っても見えない。画面を開いたときの要求をブラウザで記録し
  （Playwright で `request` を拾う）、同じ本文の要求が 2 回以上出ていないかを数える。実例のアプリでは、一覧のキャッシュの判定
  （画面の文書から作る署名）が、別の一覧の答えで文書が足されるたびに「変わった」と判断し、重い一覧を 2 回ずつ取っていた。
  開発モードの React StrictMode が出す重複（同じミリ秒に 2 本）とは分けて数える
- 実行計画の時間で小さな変更を比べない。`EXPLAIN ANALYZE` は計測自体の負荷が乗り、1 回ごとのぶれも大きい。
  比べるときは、同じクエリを直接 15 回ほど流した中央値を、変更前・変更後で交互に取る。結果の行のハッシュも比べて、
  答えが変わっていないことを同時に確かめる
- **同じ認可の判定を 2 回していないか**。ルーターのミドルウェアを `/:id` と `/:id/*` の両方に掛けると、
  フレームワークによっては `/:id/*` が `/:id` そのものにも当たり、詳細の API だけ判定が 2 回走る（Hono など）。
  1 リクエストの文を `pg_stat_statements` で並べ、同じ文が同じ回数ずつ重なっていたら疑う。
  まとめるなら、リクエストのオブジェクトをキーにしたメモ（`WeakMap<Request, …>`）に**通った判定だけ**を、
  呼び出した人と対象の ID の組で覚える。落ちた判定は覚えない

## 4. CPU: プロファイルを取る

DB を使わないのに遅いときに使う。

- Cloudflare `wrangler dev`: Chrome DevTools Protocol の窓口が `ws://127.0.0.1:9229/ws` にある。
  WebSocket でつなぎ、`Profiler.enable` → `Profiler.start` → リクエストを数十回 → `Profiler.stop`。
  返ってきたプロファイルの `samples` と `timeDeltas` から、関数・ファイルごとの自己時間を集計する
  （実例: graphica の `scripts/bench/profile.ts`）
  - **Origin ヘッダーが無い接続は理由なしに切られる**（コード 1006）。
    `Origin: https://devtools.devprod.cloudflare.dev` を付ける
- Node: `node --cpu-prof`、または `--inspect` で同じ手順
- 計測の前に数回リクエストを送って温めておく（初回のコンパイルを数えない）

読み方:

- 上位の関数がアプリのコードなら、そこを直す
- **上位にループ自身が足したものが無いかを先に見る**。デバッグ用の二重実行・念のための検証・詳しいログ・計測用のフックは、
  入れた本人が忘れやすい。ISUCON2026 の優勝チームでは、エージェントが自分で入れた画像の検査（二重に実行して結果を比べる
  デバッグの仕組み）が CPU の約 86% を使っていた。外してよいのは、ループが足したことを git の履歴か台帳で示せるものだけ。
  アプリにもともとある入力やサイズの検証は、似て見えても外さない（security-gates.md の「最初に却下する案」）。
  外すときは、外す前と後で結果が一致することを確かめ、セキュリティだけのレビューも通す
- **平ら**（フレームワークの中に薄く広がり、1 か所に偏らない）なら、細かい書き換えでは縮まない。
  仕組みを変える案（静的化・HTML のキャッシュ）を考える。それが security-gates.md の
  「最初に却下する案」に当たるなら、深追いせず DB など別の軸に移る。平らだと分かったこと自体を台帳に残す

## 5. 転送量

- ページの HTML / ペイロードの大きさは、**圧縮後で**測る（`curl -s <url> | gzip -c | wc -c`）。
  本番は gzip / brotli で送るので、生の大きさで決めると見立てを誤る（graphica のトップは生 104KB、gzip 後 12KB。
  大半は繰り返しの多い class 名で、よく縮んでいた）
- 中身の内訳は、HTML 本体・インラインのスクリプト（RSC のペイロードなど）・埋め込みデータに分けて測る。
  「何かが大きそう」という推測で手を入れない
- 減らすときも、整合性チェック（ページに必要な文字列が含まれるか）が通ることを確かめる
- **画像を軽くする変更は、見た目が落ちていないかを別に確かめる**。点数も整合性チェックも画質を見ていない。
  表示される大きさから要る画素数を計算し、配る画像がそれを下回らないかを比べる。
  `object-fit: cover` で切り抜く画像は、枠より横長なら高さを埋めるまで拡大されるので、要る幅は
  `max(枠の幅, 枠の高さ × 画像の横長の比)` になる
  （実例: 正方形のタイルに 2:1 の画像。タイルの幅だけで `sizes` を決めると粗くなり、別のエージェントのレビューで見つかった）

## 5.5 ページの表示の速さ（Web Vitals）

- **診断のチェック項目は「直せる場所」で、「効く量」ではない**。Lighthouse の「LCP の画像を遅延読み込みにしない」
  「fetchpriority=high を付ける」のような項目を候補にする前に、LCP の内訳（最初のバイト・読み込み開始までの待ち・
  読み込み・描画までの待ち）を見て、その項目が直す部分が大きいかを確かめる。
  実例: 読み込み開始までの待ちが 0.2 秒ほどの LCP で先読みと優先度を付けても、LCP は縮まず（交互 6 組、比 0.99）、
  先読みはほかの先読みや CSS と帯域を取り合うだけだった

## 6. GPU（描画）

- **パスごとの時間を引き算で出す**: 「焼き直し + 合成」のフレームから「合成だけ」のフレームを引くと、焼きの分が出る。
  フレームの種類を分けて測っておけば、プロファイラ無しで当たりが付く
- **全画素で計算しているが、一部にしか効かない処理を探す**: マスクが 0 の所でも計算している画材
  （月から遠い空の月、稜線より上の稜線、水平線より上の水面、手前の層に塗り直される奥の層）。
  DB の「使っていない列のためのクエリ」に当たる。外す境界（効く幅）はコメントで処理の側にも書く
- 道具: Instruments の Metal System Trace（パスと command buffer の時間）、Xcode の GPU キャプチャ（シェーダーの行ごとのコスト）
- 効果の帰属: 全シナリオが同じシェーダーを通るので、`--touched` は効く範囲が限られた変更（季節だけの添景など）で使う。
  それ以外では「変更していないフレームの種類が動いていない」ことで確かめる
