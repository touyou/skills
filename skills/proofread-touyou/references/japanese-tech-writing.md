# 日本語技術文書の文章規範（touyou 用・柵つきリファレンス）

`proofread-touyou` の補助リファレンス。**表記・用語・参照の「一貫性」や「読者が辿れるか」で迷ったときだけ**開く。

## 使い方（最重要）

- これは **スタイル書き換えのチェックリストではない**。校正の主役はあくまで SKILL.md の「迷ったら触らない」「文体・リズム・ゆらぎを保護」。
- **A 節だけを使う**（指摘のみ・肉声に触れない一貫性/明確さ）。
- **B 節は "やってはいけないことの記録"**。技術文書の一般規範だが touyou さんの文体と衝突するので、**規範を盾に直さない**。むしろ「これをやりたくなったら止まる」ためのリスト。
- A 節でも、書き換えを押し付けず「揃えては？」「これ読者に伝わる？」と**指摘するだけ**。揃える方向は本人に委ねる。

---

## A 節：取り入れる（指摘のみ・肉声に触れない）

肉声を一切変えずに、技術文書としての一貫性・明確さだけを上げる観点。見つけたら指摘する。

### A1. 表記ゆれ（同じ語の不統一）
同じ概念が記事内で違う綴り・カナ・英語で出てくる。
- 例:「ウィジェット」と「Widget」、「コントロールセンター」と「Control Center」、「技術債」と「技術的負債」。
- 指摘するだけ。どちらに揃えるかは本人に委ねる（地の文・コード識別子・シリーズ全体のどれに合わせるかは本人判断）。

### A2. 読者が辿れない／別物に見える参照
地の文に、読者がリンクをたどれない識別子や、別物に見える記法が残っている。
- 例: WWDC セッション番号を `(#343)` と書く → GitHub の issue/PR 参照に見える（同じ文書が本物の issue にも言及していると特に誤読する）。
- 例: `実機 (R)` のような**凡例なしの略号**。
- 「これは読者に何を指すと伝わるか？」と確認するだけ。消すか・凡例を付けるか・表記を変えるかは本人判断。

### A3. 数字・単位・記号の表記の一貫性
半角/全角、スペースの有無、記号の使い方が記事内で揺れている。
- 例: `(#343)` と `(セッション 343)`、`30 分` と `30分`。
- 揺れている事実だけ指摘する。

### A4. 箇条書き・表の体裁の一貫性
同じ列・同じ並びの中で表記体系が混ざっている。
- 例: 1つの表の「展開先」列にカタカナ（ウィジェット）と英語（Live Activity）が混在。
- 「列の中で揃えては？」と指摘するだけ。

### A5. コード識別子と地の文の対応
コードブロックに出る識別子と、地の文での呼び方がズレている（綴り・大文字小文字）。
- 例: コードは `SubTask`、地の文は「サブタスク」と「Subtask」が混在。
- 実害がなければ無理に統一しない。明らかな不一致だけ指摘。

## B 節：取り入れない（touyou さんの文体として保護）

これらは日本語技術文書では「よし」とされがちな規範だが、**touyou さんの肉声を削るので採用しない**。「指摘してはいけない」リスト＝SKILL.md「迷ったら触らない」の具体化。

- **漢字／ひらがなの強制統一**（補助動詞・形式名詞のひらがな化など。例: 「出来る→できる」「事→こと」を一律に）
  → 漢字とかなの揺れ自体が肉声。一律変換しない。
- **一文を短く分割する**
  → 連用形（〜だけで、〜るので、〜ながら）で繋ぐ長文が touyou さんのリズムの本体。切らない。
- **体言止めを避ける／です・ます に揃える**
  → 体言止め（「〜見えるパターン。」）や常体／敬体のゆらぎは意図的。硬化させない。
- **接続詞を減らす／硬い接続詞に置換**（「ただ」「ですが」「そこで」→「したがって」等）
  → 柔らかい接続詞は保護対象。
- **「重要なのは」等のメタ進行を一律除去**
  → 過剰な決め台詞は AI 臭4項目として別途扱うが、**元からあるものを規範で機械的に削らない**。
- **二人称回避・行為者主語化・架空人物禁止**
  → touyou さんは「自分は」一人称＋読者への語りかけが文体。役割名へ機械置換しない。
- **口語副詞・砕けた表現の硬化**（「本当に」「結構」「ちょっと」→「実に」「相当」「概ね」）
  → 保護リスト。置換しない。
- **推量・留保の削除**（「〜と思います」「〜っぽくて」「〜ようでした」→断定）
  → 留保は意図的なゆらぎ。事実未確認の留保はむしろ正しい（断定の方が嘘になる）。
