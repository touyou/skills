# Bug-Prone Patterns ルーブリック (1-5)

コードに「バグを埋め込みやすい構造」がどれくらいあるかを判定する。**5 が「埋め込みにくい」**、1 が「埋め込みやすい」。

## 判定対象

サンプリングされた代表ファイル群。

## 評価軸（言語横断 + TS 固有）

### 言語横断

1. **null/undefined の扱い**: 型レベル、ガード、optional chaining の使い方
2. **エラーハンドリング**: try-catch の粒度、握りつぶし、再 throw
3. **状態の局所化**: グローバル state / 副作用の散らばり
4. **境界の防御**: 外部入力 / API 結果 / DB 結果がバリデートされているか
5. **並行/非同期**: race condition、await 漏れ、未処理 Promise

### TypeScript 固有

6. **`any` / `as` の使用**: 型システムを迂回している箇所
7. **discriminated union vs `if-else` チェーン**: 網羅性が型で保証されているか

## レベル定義

### 5 — bug が埋め込みにくい

- `any` / 危険な `as` が0または極少数（型システムが信頼されている）
- 外部入力は zod/yup 等でバリデートされてから内部に入る
- エラーは具体的に catch され、再 throw か明示的なフォールバックがある
- async 関数で await 漏れがない（`@typescript-eslint/no-floating-promises` 違反なし）
- グローバル可変状態がない、または1箇所に集約されている

### 4 — おおむね健全

- レベル5の条件をほぼ満たすが、1-2箇所に `any` または握りつぶし catch がある
- 大半の境界は守られているが、一部「内部呼び出しだから大丈夫」と省略されている

### 3 — 平均的

- `any` が散見される（10箇所程度）
- catch ブロックで `console.error` だけして握りつぶしている箇所が複数
- バリデーションの抜け（外部 API のレスポンスをそのまま使う等）がある
- 明らかな race condition は見えないが、await 漏れの兆候が一部ある

### 2 — bug が埋め込まれやすい

- `any` / `as unknown as` が頻発（スコア対象ファイルの大半に出現）
- エラーが catch 後に消えている（再 throw も log もしない）
- 外部入力のバリデーションがほぼない
- 複数箇所のグローバル可変状態が並行に書き換えられる構造

### 1 — bug 温床

- 型がほぼ機能していない（`any[]` や `Record<string, any>` が中核に居座る）
- 例外を上層まで握りつぶす設計が体系化されている
- async 処理で fire-and-forget が常態化

## 軸別のサンプリング難易度

7軸のうち、**少数サンプルで判定できるもの** と **wide sample が要るもの** がある:

| 軸 | 必要な観察範囲 | 少数サンプルでの判定可否 |
|---|---------------|------------------------|
| 1. null/undefined 扱い | 各ファイル内で完結 | ✅ 数ファイルで判定可 |
| 2. エラーハンドリング | 各ファイル内 + パターン蓄積 | ⭕ 5-10 ファイルあれば |
| 3. 状態の局所化 | プロジェクト全体俯瞰必須 | ❌ wide sample 必須 |
| 4. 境界の防御 | entry point / API 層を見る必要 | ⭕ entry point を含めれば |
| 5. 並行/非同期 | 各ファイル内（floating promise）+ 全体（race） | ⚠️ 部分的に可 |
| 6. `any` / `as` 使用 (TS) | 各ファイル内 | ✅ 数ファイルで判定可 |
| 7. discriminated union vs if-else | 各ファイル内 | ✅ 数ファイルで判定可 |

**サンプル < 8 ファイルの場合**、軸 3（状態の局所化）と軸 5 の race condition は判定対象から外す。残りの軸で評価する。

## 判定手順

1. サンプリングされた各ファイルで上記軸を確認（観察できる軸だけ）
2. 観察された具体的な bug-prone シグナル数をメモ（"any 12箇所"、"floating promise 3箇所" 等）
3. 全体傾向から 1-5 を1つ選ぶ
4. rationale に「観察した軸」「観察できなかった軸」を分けて書く

## サンプル不足時の挙動

サンプリングされたファイル数が **8 未満** で、評価できなかった軸が 3 軸以上ある場合:

- **default = 3** にする
- 観察できた軸で強いポジティブ/ネガティブシグナルが 2 つ以上揃ったときのみ 4 / 2 に振る
- `confidence: "low"` を必ず設定する
- rationale で「軸 X, Y, Z は観察できず」を明記

## 注意

これは「実際にバグがあるか」ではなく「**構造としてバグを埋め込みやすいか**」を見る。lint 違反数（Tier 1）と相関するが、相関しない場合もある:

- Tier 1 高評価 / Tier 2 低評価: ルールは通るが、エラー握りつぶし等の設計上の問題
- Tier 1 低評価 / Tier 2 高評価: lint 違反は多いが、そのほとんどが命名や空白等で構造的問題ではない

## rationale の書き方

⭕ "any が src/api 配下に14箇所、catch (e) { console.log(e) } の握りつぶしが3箇所、await 漏れ警告が2件。zod バリデーションは entry point に存在。Score 3."

❌ "Some risky patterns observed"
