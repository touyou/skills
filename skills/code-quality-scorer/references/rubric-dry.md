# DRY ルーブリック (1-5)

「重複の少なさ」だけでなく **「重複と抽象化のバランス」** を判定する。早すぎる/過剰な抽象化も減点対象。

## 判定対象

サンプリングされた代表ファイル群（重複パターン、抽象の使われ方）。

## 評価軸

1. **真の重複**: コピペされた同一/ほぼ同一ロジックの存在
2. **抽象化の適切さ**: 抽象化された箇所が、実際に多様性を吸収しているか（"rule of three" を満たすか）
3. **過剰抽象**: 1-2箇所でしか使われない抽象、設定可能項目が増えただけのジェネリック関数の有無
4. **設定の重複**: 同じ定数/設定値が複数箇所にハードコードされていないか

## レベル定義

### 5 — DRY 適切

- 同一ロジックの目立った重複がない
- 抽象化された関数/クラスは3箇所以上から呼ばれており、複数のケースを実際に吸収している
- 過剰抽象（1-2箇所しか使わない汎用化、巨大な設定オブジェクト型）が見えない
- 共通定数が単一の source of truth に集約されている

### 4 — おおむね DRY

- 真の重複は最小限
- ほぼ全ての抽象が機能しているが、1-2箇所「これは inline でよかった」という抽象がある
- 重要な定数は集約されているが、稀にマジックナンバーが散らばる

### 3 — 重複と抽象化が混在

- 似たコードが2-3箇所に散らばっており、本来は共通化できる箇所が見える
- もしくは逆に「使い回しのために抽象化したが、結果として呼ぶ側が複雑になっている」抽象がある
- 「DRY を意識し始めたが完了していない」状態

### 2 — 重複が目立つ

- 明確なコピペが複数箇所に存在（同じバリデーション、同じ API 呼び出し型）
- 共通化されていない設定値が複数のソースに散らばる

### 1 — DRY が破綻

- ほぼ同一の関数が3箇所以上に存在し、片方を直しても他方が古いまま
- もしくは過剰抽象により、共通関数が肥大化（10以上のオプション、複数モードを内包）

## 判定手順

1. ファイル横断で類似ブロックを探す（関数名、シグネチャ、構造）
2. 共通化された関数/クラスがどこから呼ばれているか確認（1-2箇所だけなら過剰抽象寄り）
3. 共通化されているべきだが分散している定数/型を探す
4. 全体傾向から 1-5 を1つ選ぶ

## サンプル不足時の挙動（重要）

DRY 判定は **本質的に横断パターンマッチング**を必要とする。サンプリングされたファイル数が **8 未満** または「責務の似通ったファイルのペア」が 3 組未満なら、十分な比較対象がなく信頼判定できない:

- **default = 3** にする（積極的に上下に振らない）
- 強い局所シグナルがあれば調整: 1ファイル内で同じ関数が複数定義されている → 2 寄り。明らかに factor された helper（`createXxx`, `xxxAdapter` 等）が多数ある → 4 寄り
- `confidence: "low"` を必ず設定する
- rationale に「DRY は cross-file 観察が要るためサンプル不足の制約あり」と明記

## rationale の書き方

具体的な重複/過剰抽象の例を1-2件挙げる:

⭕ "src/api/users.ts と src/api/orders.ts に酷似した fetch wrapper が重複（25行 × 2）。一方 createGenericModal という 8引数の関数があり、呼び出し2箇所のみで過剰抽象。Score 3."

❌ "Some duplication exists, abstraction could be improved"
