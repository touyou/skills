# retrospective

「同じ指摘を繰り返し受ける」「同じミスを繰り返す」というシグナルを 2 系統の情報源から掘り起こし、AGENTS.md / CLAUDE.md / スキル / memory に恒久ルールとして反映するための候補を洗い出す。`harness-intake` が「磨いたハーネスを他プロジェクトへ展開する」役割なのに対し、このスキルは**その前段**として「自分のハーネスの中で何を磨くべきかを継続的に発見する」役割を担う。

## 鉄則

- **振り返りだけなら候補を提示する**。具体的なルール反映まで依頼されている場合は、その範囲で編集する。新たな恒久ルールや適用範囲の拡大は反映先と差分を提示して確認し、既存の許可を再確認しない。
- **「繰り返し」をシグナルの中心に置く**。1 回きりの失敗はその場の修正で足りることが多い。2 回以上出現したものを優先する。
- **既に明文化済みのルールと照合してから提案する**。AGENTS.md に書いてあるのに守られていない場合は「ルール追加」ではなく「ルールが効いていない理由 (書き方・場所・強調不足)」を掘る。

## 引数

- `日数` (省略時 14): 対象期間。例 `/retrospective 30` で直近 30 日。

## 情報源 1: セッションログからの失敗抽出

対象プロジェクト・期間に紐づく、現在利用可能な会話履歴ツールまたはログから、次のシグナルを抽出する:

- **ユーザーの修正指示**: 「そうじゃなくて」「違う」「戻して」「〜しないで」等、エージェントの行動を打ち消す発話
- **不満・徒労の表明**: 「また同じ」「前も言った」等
- **エージェント自身の失敗報告**: テスト失敗からのやり直し、誤ったファイル編集の取り消し、TaskStop での中断

履歴が取得できなければ取得できた情報源だけを使い、対象範囲と欠測を報告する。他プロジェクトのログまで無差別に探索しない。

抽出したら「何をしようとして → 何を間違え → どう正されたか」の 3 点に正規化する。

## 情報源 2: PR レビュー指摘の集約

自分が author の PR に付いたレビューコメントを対象期間で集約する:

```bash
GH_USER=$(gh api user --jq '.login')
SINCE=$(date -v-${DAYS}d +%Y-%m-%d)  # macOS。GNU date なら date -d "-${DAYS} days"

# 自分の PR (merged 含む) を列挙
gh pr list --author "$GH_USER" --state all --search "updated:>=$SINCE" \
  --limit 1000 --json number,title,url

# 各 PR のレビューコメントを取得 (自分以外のコメントに絞る)
gh api --paginate --slurp "repos/{owner}/{repo}/pulls/$PR_NUMBER/comments" \
  | jq --arg me "$GH_USER" --arg since "$SINCE" 'add | map(select(.user.login != $me and .created_at >= $since)) | .[] | {id, author: .user.login, path, body, created_at}'
```

bot レビュアー (CodeRabbit 等) の指摘も含める。「AGENTS.md に書かれていないから毎回指摘される」パターンの検出が目的なので、人間/bot は区別せず同種指摘の再出現を数える。

## クラスタリングと候補化

2 系統の抽出結果を突き合わせ、同種のものをクラスタにまとめる:

1. **同一性の基準**: 「何を間違えたか」の要旨で束ねる (例: 「テスト実行せずに完了宣言」「コミットメッセージの規約違反」「特定 API の誤用」)
2. **出現回数と情報源の幅**を数える。同じ PR コメントの引用やセッション内の再掲は同一イベントとして数え、別の失敗が起きた回数と区別する。両系統に出ているクラスタは優先度を上げる
3. 各クラスタについて、**既存の明文化と照合**する: AGENTS.md / CLAUDE.md / 関連スキル / memory を rg で検索し、
   - 未記載 → 「新規ルール候補」
   - 記載あり → 「ルールが効いていない」候補 (記述位置・具体例不足・矛盾する他ルールを疑う)

## 候補の提示と反映

候補を優先度順にユーザーへ提示する:

```markdown
## retrospective 結果 (直近 14 日)

| # | クラスタ | 出現 | 情報源 | 既存ルール | 提案 |
|---|---|---|---|---|---|
| 1 | テスト未実行のまま完了宣言 | 3回 | セッション×2 + PR×1 | 無し | CLAUDE.md「検証の規律」に追記 |
| 2 | import 順の指摘 | 4回 | PR×4 | AGENTS.md に記載済み | lint ルール化を提案 (明文化では効いていない) |

各候補の反映先ドラフト: (差分プレビューを提示)
```

**ユーザーが承認したものだけ**反映する。反映先ごとの作法:

- **AGENTS.md / CLAUDE.md**: 該当セクションに追記。恒久ルールなので「なぜ」を 1 行添える
- **スキル**: 該当スキルの鉄則・注意事項に追加し、スキルの semver を bump
- **memory**: feedback タイプで保存 (**Why** / **How to apply** を付ける)
- 反映方法は対象リポジトリの規約と依頼に従う。ローカル編集や memory 更新だけの依頼で PR を勝手に作らない。抽象的な「必ず再確認する」ルールを増やさず、失敗を防ぐ具体的な条件・コマンド・出力を示す。

汎用化できるパターンだった場合は、仕上げに `harness-intake` での起票を提案する (このスキルが前段、`harness-intake` が後段)。

## 由来とブラッシュアップ方針

「AGENTS.md に書かれていないから毎回指摘される」を検出可能なシグナルとして扱う、という発見を型化したもの。クラスタリングの同一性基準と「明文化済みなのに効かない」ケースの対処パターン (lint 化・hook 化・記述位置の変更) の実例を集めて育てる。

## 依存

- `gh` CLI と GitHub 認証 (情報源 2 を使う場合)
- セッションログへのアクセス (情報源 1 を使う場合。無ければ情報源 2 のみで動く)
