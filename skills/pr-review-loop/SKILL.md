# レビューループ

PR の発見・分類・修正・再レビューを分け、修正可能な指摘がなくなるか上限に達したら終了する。マージはこのスキルの範囲に含めない。

## 実行範囲と設定

- 自分の PR は `auto-fix`、他人・bot の PR は `comment-only` が既定。明示フラグ > `.claude/pr-review-loop.local.md` の `default_mode` > author 判定の順で決める。両フラグ指定は入力エラー。
- モードは作業方法を選ぶもの。投稿・push の許可はユーザーの依頼に従う。レビュー結果だけを求められた場合はローカルに結果を返し、投稿が必要なら完成した本文を提示して確認する。既存の許可は再確認しない。
- 設定の完全版は [references/configuration.md](references/configuration.md)。未設定のコマンドは規約・CI・package.json / Makefile 等から決める。利用不能な format/test コマンドを作り上げない。
- 特定のプラグインは必須にしない。利用可能な専門レビューアがなければ同じ観点を自分で読む。小さな差分は直接レビューし、独立した観点に分ける利益がある場合だけ必要なレビューアを起動する。

## 1. 対象と証拠を固定する

PR URL があればそのリポジトリを優先し、番号だけなら現在のリポジトリを使う。引数なしなら現在のブランチの PR を取得する。URL の番号だけ抜き出して別リポジトリに適用しない。

```bash
gh pr view "$PR_NUMBER" --repo "$OWNER/$REPO" \
  --json number,url,author,headRefOid,baseRefOid,headRefName,baseRefName,isCrossRepository
```

`REVIEW_HEAD` と `REVIEW_BASE` に取得した SHA を保持し、その差分と周辺コードをレビューする。auto-fix では PR head を checkout したことを確認する。作業中の変更がある、別ブランチで作業している、fork の PR を扱う場合は専用 worktree と適切な push 先を用意する。既存変更を stash・restore して片付けない。

既存コメント・レビュー・resolved 状態は [references/github-review.md](references/github-review.md) に従って集める。同じ問題の再投稿は避けるが、resolved という印だけで未修正や再発を隠さない。取得失敗は「既存指摘なし」ではなく未確認として記録する。

## 2. 発見する

レビューアには次を渡す。親が先に出した結論や他レビューアの結果は渡さない。

```text
指定した PR の base/head SHA と対象差分を、担当観点からレビューしてください。
初回は全差分、2 回目以降は修正差分と影響を受ける呼び出し元・テストを読んでください。
各発見に、場所 (path/line/side)、内容、根拠、重要度 (🔴/🟡/🟢)、確度 (high/medium/low) を付けてください。
確度が低いものや軽微なものも含めて全部出し、絞り込みは後段に任せてください。
発見がなければ「無し」。各発見は 1〜3 文で、前置きと総括は不要です。
コード編集や外部への投稿は行わず、未確認の観点と取得失敗も報告してください。
```

一部のレビューアが失敗したら未確認観点を自分で補うか、未完として残す。未確認を 0 件扱いにして APPROVE しない。全て失敗し、自分でもレビューできない場合は失敗として終了する。

## 3. 分類して出力先を決める

各発見を `category` (`actionable/discussion/out-of-scope`)、`severity` (`🔴/🟡/🟢`)、`confidence` (`high/medium/low`)、`path/line/side/body` に正規化する。種別・重み・確度を混ぜない。確度欠落時は根拠を読んで補い、判断できなければ `low` とする。

- `actionable`: 要件やコードに根拠があり、修正方向が明確。
- `discussion`: 仕様解釈やトレードオフの判断が必要。テストが通ることだけで正解扱いしない。
- `out-of-scope`: 今回の変更から生じていない既存の問題。変更されていない呼び出し元で起きる回帰はスコープ内。サブモジュールも参照先変更の影響はスコープ内。

下表を上から評価し、最初に一致する出力先に一度だけ振り分ける。

| 条件 | 出力先 | 自動修正 |
|---|---|---|
| out-of-scope（重み・確度は任意） | スコープ外：場所・要旨・件数 | しない |
| discussion（重み・確度は任意） | 要相談：根拠・選択肢・件数 | しない |
| actionable + low（重みは任意） | 要確認：場所・根拠・件数 | しない |
| actionable + high/medium + 🟢 | 軽微：場所・根拠・件数 | 許可範囲内で行う |
| actionable + high/medium + 🔴/🟡 | 修正対象、またはインライン（行を指せなければ本文） | 許可範囲内で行う |

全 27 組（3 種別 × 3 重要度 × 3 確度）の出力先が一意に決まり、分類後の件数合計が重複統合後の発見数と一致することを確認する。不正な値は分類を直し、捨てない。

## 4a. 修正する（auto-fix）

1. 修正前の head を `PREV_HEAD` に記録する。関連指摘を一つの修正グループにまとめ、触るファイルと生成するファイルを記録する。
2. 修正し、必要なコード生成 → format → 変更に適した lint/test の順で実行する。失敗したテストを通すためだけに期待値を実装へ合わせない。
3. 成功したグループだけコミットする。規約に従い対象ファイルだけ stage する。
4. 失敗時は原因を記録し、このグループで加えた差分のみを取り消す。既存変更が混ざる場合にファイル全体を restore しない。新規ファイルも自分が生成したものだけを削除する。`git clean -fd` は使わない。
5. 許可された push を実行する。競合しないリモート更新は一度だけ rebase して関連テストを再実行する。競合したら `git rebase --abort`。force push はしない。認証等の失敗は復旧可能なコミットと作業場所を報告する。
6. `git diff "$PREV_HEAD" HEAD` を再レビューする。`PREV_HEAD` は push 後に上書きしない。修正差分に加え、影響を受ける呼び出し元とテストも読む。

既定 `max_iterations=5`。同じ問題への修正試行は 2 回まで。指摘 ID はパスと問題の要旨で保ち、行移動だけで別件にしない。テスト成功時に試行回数を消さず、再レビューで解消を確認する。

修正対象 0 件、全対象が修正不能、同一問題 2 回、全体上限のいずれかで終了する。後三者は「全解消」と報告しない。low・discussion・スコープ外も結果に残す。

## 4b. 投稿する（comment-only）

投稿が許可されていれば [references/github-review.md](references/github-review.md) の手順で 1 件の Pull Request Review にまとめる。コードは編集しない。

| 状態（上から判定） | event |
|---|---|
| 自分の PR | COMMENT |
| actionable + high/medium + 🔴/🟡 がある | REQUEST_CHANGES |
| レビュー未完、重要な仕様が未解決、根拠のある重大な懸念が保留中 | COMMENT |
| 上記なし（軽微な提案のみ、または指摘なし） | APPROVE |

APPROVE はレビュー上の判断で、CI 成功やマージ可能性の保証ではない。

## 5. 終了時の状態と報告

最新 head/base と CI、`mergeStateStatus` を取り直す。head が変わったら差分を追加レビューし、古い SHA の結果を最新の結果として扱わない。

- `CLEAN`: GitHub 上の現時点の状態として記載。意味上の競合がない保証にはしない。
- `BEHIND`: base 遅れとして報告。許可済みの auto-fix で branch 更新した場合は新 head の差分・CI を確認する。
- `DIRTY/BLOCKED/UNSTABLE`: コンフリクトや未完の要件を報告する。
- `UNKNOWN` その他の未確定状態: 最大 2 回再取得し、残れば未確定とする。

最終報告は対象 PR・レビュー SHA・モード・終了理由・修正と未解消の件数・テスト結果・実際に投稿した URL/event を簡潔に示す。全分類の指摘を本文またはリンク先に残し、未実行・取得失敗を明記する。
